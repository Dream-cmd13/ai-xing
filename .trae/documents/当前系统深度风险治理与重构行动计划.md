# 当前系统深度风险治理与重构行动计划

## Summary

- 目标：基于当前仓库 `d:\aixing\okr-ai` 的真实代码与 SQL 结构，判断系统是否仍存在高风险，是否需要重构表结构或项目代码，并给出最迫切治理事项与执行顺序。
- 总结论：**系统仍然存在明确的结构性高风险，需要继续重构，但不需要推倒重写。**
- 核心判断：
  - 当前系统已经完成了若干关键修复：自动保存已移除、手动保存已落地、乐观锁已接入、未保存离开提醒已补齐、工作台已改为精准任务加载、路由级按域加载已开始生效。
  - 但这些修复主要解决了“可用性”和部分并发覆盖问题，**尚未彻底解决数据权限、保存原子性、状态边界和数据模型颗粒度**这四类系统级风险。
  - 当前最迫切需要做的事情，不是继续改 UI，也不是继续局部修 bug，而是先把**数据安全与写入一致性**收口。

## 最终判断

- 是否还存在明显问题：**存在，而且不是零散 bug，而是可持续放大的结构性问题。**
- 是否有高风险需要治理：**有，且至少有 3 个 P0/P1 级高风险需要尽快治理。**
- 是否需要重构表结构：**需要，但建议分阶段、按热点域渐进重构，不建议一次性全表重建。**
- 是否需要重构项目代码：**需要，并且优先级高于表结构重构。**
- 当前最迫切需要做的事情：**先治理权限与写入一致性，再治理状态管理与数据模型。**

### 2. 当前最严重的风险排序

#### P0-1：RLS 读权限过宽，存在越权读数风险

- 关键文件：
  - `d:\aixing\okr-ai\sql\00_one_click_schema.sql`
  - `d:\aixing\okr-ai\data.ts`
- 证据：
  - `users/departments/processes/strategy/businesses/tasks/system_roles/settings` 全部对 `authenticated` 开放 `SELECT USING (true)`。
  - 当前数据层仍有大量全表查询，如 `getUsers()`、`getDepartments()`、`getProcesses()`、`getBusinesses()`、`getTasks()`。
- 问题本质：
  - 任何已登录用户都可以读取核心业务表的全部数据，违反最小权限原则。
  - 对于 `settings`、`system_roles`、组织架构、流程设计等管理类数据，这已经不是“代码味道”，而是明确的安全边界过宽。
- 影响：
  - 一旦账号体系扩大，普通成员可读全部管理配置、组织信息、任务与流程数据。
  - 后续即便前端 UI 隐藏入口，也无法弥补后端 RLS 已经放开的事实。

#### P0-2：保存链缺少真正原子性，域内仍可能部分成功

- 关键文件：
  - `d:\aixing\okr-ai\hooks\useAppActions.ts`
  - `d:\aixing\okr-ai\data.ts`
- 证据：
  - `handleSave()` 仍然以域数组顺序执行保存。
  - `saveDepartmentsDomain()`、`saveUsersDomain()`、`saveSystemRolesDomain()`、`saveBusinessesDomain()`、`saveProcessesDomain()` 仍是逐条 `await` 删除/新增/更新。
- 问题本质：
  - 虽然已经从“全量一键保存”收口到“按域保存”，但**域内写入仍没有事务边界**。
  - 例如部门域保存中，先删后增后改，只要中间某一步失败，就会留下半成功状态。
- 影响：
  - 用户看到“保存失败”，数据库却可能已经完成了一部分变更。
  - 这类中间态最难排查，也最容易让前端基线和数据库真实状态脱节。

#### P0-3：新增/删除缺少版本保护，乐观锁只覆盖 update

- 关键文件：
  - `d:\aixing\okr-ai\data.ts`
- 证据：
  - `updateTask/updateUser/updateDepartment/updateProcess` 等更新路径使用了 `row_version` 条件。
  - 但多个删除操作仍只按 `id` 删除，没有版本条件。
  - 多个新增操作仍通过 `upsert(...).select('*').single()` 落库。
- 问题本质：
  - 当前系统只做到了“更新时的乐观锁”，没有做到“完整生命周期的乐观锁”。
  - 删除和创建在并发场景下仍可能误删、重复提交、覆盖式创建。
- 影响：
  - 他人修改后的记录可能被旧页面直接删除。
  - 重复点击、请求重试、客户端 ID 重用时，`upsert` 语义会放大歧义。

## 最迫切需要做的事

### 第一优先级结论

- 当前最迫切需要做的不是表结构大重构，也不是继续页面级体验优化。
- **第一优先级必须是：先把“后端权限边界 + 写入一致性边界”补齐。**

### 原因

- 如果继续在现有 RLS 与写入链路上叠加功能，问题会从“能用但有风险”升级为“数据不可信、权限不可信”。
- 与性能或页面结构相比，权限泄露与半成功写入属于更高等级风险，后果更难修复。

### 具体定义

- 先收口 `RLS`。
- 再收口 `delete/insert/update` 的并发语义。
- 再把域内保存改为真正可解释、可回滚、可定位失败点的写入模式。

## Proposed Changes

### 阶段一：P0 数据安全与一致性治理

#### 1. 收紧 RLS 策略，按业务角色最小化读取范围

- 涉及文件：
  - `d:\aixing\okr-ai\sql\00_one_click_schema.sql`
  - `d:\aixing\okr-ai\data.ts`
- 改什么：
  - 移除管理类表对所有已登录用户的 `SELECT USING (true)`。
  - `settings/system_roles/processes/businesses/strategy` 优先改成仅管理员或特定角色可读。
  - `tasks` 改为按 `owner_id/participant_ids/approver_ids/可见范围` 约束读取。
  - 对确实需要全员可见的字段，优先考虑只暴露“投影视图”而不是开放整个表。
- 为什么：
  - 安全边界必须在数据库层收口，不能只靠前端菜单权限。
- 怎么做：
  - 先按现有角色模型实现最小可用版本。
  - 如前端确实需要全局展示但不需要完整行，可增加 `view` 或 RPC。
- 验收标准：
  - 普通成员无法直接读取系统设置、系统角色、全量流程与全量业务定义。
  - 任务查询仅返回当前用户应看到的任务。

#### 2. 为删除与创建补齐并发控制语义

- 涉及文件：
  - `d:\aixing\okr-ai\data.ts`
  - `d:\aixing\okr-ai\sql\00_one_click_schema.sql`
- 改什么：
  - 删除操作由“按 `id` 删除”改为“按 `id + row_version` 删除”。
  - 新增操作从宽泛 `upsert` 改为显式 `insert`，只在有明确幂等需求时使用受控 `upsert`。
  - 统一冲突错误语义，让前端能区分“版本冲突”“重复提交”“权限拒绝”。
- 为什么：
  - 乐观锁必须覆盖完整写入生命周期，不能只保护 update。
- 怎么做：
  - DAO 层新增受控删除方法，例如 `deleteXxx(id, rowVersion)`。
  - 对于可能重复提交的入口，明确幂等键，不再混用 `upsert` 兜底。
- 验收标准：
  - 旧页面无法误删已被他人更新的记录。
  - 重复点击提交不会悄悄变成覆盖式写入。

#### 3. 把“域内多步保存”迁移为后端事务/RPC

- 涉及文件：
  - `d:\aixing\okr-ai\hooks\useAppActions.ts`
  - `d:\aixing\okr-ai\data.ts`
  - `d:\aixing\okr-ai\sql\00_one_click_schema.sql`
- 改什么：
  - 对 `departments/users/systemRoles/businesses/processes` 等存在批量保存的域，新增 RPC/SQL function 作为事务边界。
  - 前端不再逐条 delete/add/update 串行拼装提交。
- 为什么：
  - 只要域内仍是前端多步提交，就永远存在半成功状态。
- 怎么做：
  - 先挑 `departments` 作为第一批，因为它既复杂又高频。
  - RPC 输入采用“基线版本 + patch 集合”或“目标快照 + 校验版本”模式，避免前端拼事务。
  - 失败返回明确结构：失败域、失败记录、冲突类型、最新版本。
- 验收标准：
  - 同一域保存失败时，数据库不出现不可解释的部分成功状态。
  - 前端能明确展示失败原因，而不是统一“保存失败”。

## Assumptions & Decisions

- 决定 1：当前项目不需要整体重写，采用“分阶段收口 + 每阶段可验证”的路线。
- 决定 2：优先级以“数据安全与一致性”高于“性能观感与代码整洁度”。
- 决定 3：把 `RLS 过宽`、`域内无事务`、`删除/新增缺少版本保护` 定义为当前最高优先级问题。
- 决定 4：表结构重构需要做，但必须后置到权限边界和写入一致性收口之后。
- 决定 5：前端代码重构重点是“状态订阅边界 + 保存职责拆分”，不是简单把文件拆多。
- 假设 1：后续执行阶段可接受新增 SQL function / RPC 作为事务与权限收口手段。
- 假设 2：后续执行阶段优先保证现有业务可用，不接受大规模一次性迁移导致长时间不稳定。

## 建议执行顺序

1. 先做 `RLS` 收口与任务可见范围重定义。
2. 再补齐删除/新增的并发保护语义。

6. 完成任务查询按场景拆分，清理 `select('*')`。
