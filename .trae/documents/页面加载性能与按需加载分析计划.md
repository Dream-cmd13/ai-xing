# 页面加载性能与按需加载分析计划

## Summary

- 目标：排查当前 React + Supabase 项目在页面加载、路由切换、表格/列表/弹窗交互中的性能与体验问题，判断是否已实现按需加载，并输出一份“问题分析 + 解决方案”的正式 md 文档。
- 结论预判：当前项目**不是按需加载优先**的模式，而是“登录后全量拉取工作空间 + 路由整包静态加载 + 多页面整棵 store 订阅”的模式，存在首屏慢、切页首包大、无关变更触发整页重渲染的系统性风险。
- 基于最新代码复查后的结论：
  - 以上三类核心问题目前**仍然存在**。
  - 最近的代码更新主要集中在“手动保存、realtime 收敛、离开提醒”，并没有触及首屏加载策略、路由拆包策略和 Zustand 细粒度订阅策略。
- 计划产物：
  - 本计划文档：`d:\aixing\okr-ai\.trae\documents\页面加载性能与按需加载分析计划.md`
  - 后续正式分析文档：`d:\aixing\okr-ai\docs\react-supabase-页面加载性能与体验分析.md`

## Current State Analysis

### 1. 当前应用启动阶段会全量拉取工作空间，不是按页面按域懒取数

- 文件：`App.tsx`
- 已确认实现：
  - 用户登录/恢复会话后，`App.tsx` 中直接调用 `getWorkspace()`。
  - 拉回的数据会一次性写入 store：`users`、`departments`、`processes`、`businesses`、`tasks`、`strategy`、`systemRoles`、`aiSettings`。
- 文件：`data.ts`
- 已确认实现：
  - `getWorkspace()` 里通过 `Promise.all` 并发执行：
    - `supabase.from('users').select('*')`
    - `supabase.from('departments').select('*')`
    - `supabase.from('processes').select('*')`
    - `supabase.from('strategy').select('*')`
    - `supabase.from('businesses').select('*')`
    - `supabase.from('system_roles').select('*')`
    - `supabase.from('tasks').select('*')`
  - 所有查询都是 `select('*')`，没有字段裁剪、没有分页、没有按页面按权限延迟加载。
- 影响：
  - 首次进入系统的等待时间随数据量线性增加。
  - 任何一个页面仅使用部分数据，也必须等待整包 workspace 就绪后才能进入。
  - `AppRoutes.tsx` 中的全屏“正在初始化系统...”会覆盖整个应用，用户无法渐进进入可用页面。
- 最新复查结果：
  - `App.tsx` 仍然在认证恢复后直接调用 `getWorkspace()`。
  - `getWorkspace()` 仍然一次性拉取 `users/departments/processes/strategy/businesses/system_roles/tasks`。
  - 新增的 `setLastSavedTasks` 只是在全量初始化后多缓存了一份任务基线，不改变“首屏全量加载”的事实。

### 2. 当前路由没有代码分割，页面组件全部进入首包

- 文件：`router/AppRoutes.tsx`
- 已确认实现：
  - `WorkbenchView`、`ProcessView`、`OrgView`、`StrategyView`、`BusinessDefinitionView`、`WeeklyView`、`UserView`、`RoleQueryView`、`TaskCenterView`、`ExecutionView`、`ReviewView`、`OkrReviewDashboard`、`MenuPermissionView`、`LoginView` 都是顶部静态 `import`。
  - 未发现 `React.lazy`、`lazy()`、`Suspense`、动态 `import()`。
- 影响：
  - 即使用户只访问一个页面，也要为其它所有主页面付出首包下载/解析成本。
  - 登录页、工作台与复杂页面无法实现“先可用，再逐页加载”。
- 最新复查结果：
  - `AppRoutes.tsx` 仍是顶部静态导入全部页面。
  - 仍未引入 `React.lazy`、`Suspense` 或动态 `import()`。

### 3. Zustand 使用方式偏粗，很多页面订阅整棵 store

- 文件：`store/useAppStore.ts`
- 已确认实现：
  - 单个 store 同时承载 `processes`、`departments`、`tasks`、`users`、`strategy`、`businesses`、`systemRoles`、`aiSettings` 以及 `isDirty/isSaving/showSaveSuccess/backendError/currentProcessId/...`。
- 文件：多个页面组件
- 已确认实现：
  - 大量页面直接 `const state = useAppStore()`，包括：
    - `WorkbenchView.tsx`
    - `TaskCenterView.tsx`
    - `ExecutionView.tsx`
    - `WeeklyView.tsx`
    - `OrgView.tsx`
    - `ProcessView.tsx`
    - `StrategyView.tsx`
    - `UserView.tsx`
    - `BusinessDefinitionView.tsx`
    - `ReviewView.tsx`
    - `RoleQueryView.tsx`
    - `MenuPermissionView.tsx`
    - `SystemConfigView.tsx`
    - `OkrReviewDashboard.tsx`
- 影响：
  - 任何一个全局字段变化，例如 `isDirty`、`showSaveSuccess`、`tasks`、`systemRoles`，都可能让整个页面重渲染。
  - 对大页面、树结构、任务看板这类高渲染成本页面尤为不利。
- 最新复查结果：
  - `useAppStore` 仍是单大 store。
  - 代表页面当前仍普遍保留 `const state = useAppStore()` 的整棵订阅方式。

### 4. 多个重页面存在全量派生计算与全量渲染，没有分页/虚拟列表

- 文件：`TaskCenterView.tsx`
- 已确认实现：
  - 基于全量 `state.tasks` 构建 `allTasks`、`filteredTasks`。
  - 同时结合 `users`、`departments`、`strategy.companyOKRs` 做多轮 `find/filter/forEach/map`。
  - 未发现虚拟滚动、分页、分段查询。
- 文件：`WorkbenchView.tsx`
- 已确认实现：
  - 每次渲染都从全量 `state.tasks` 派生 `allMyTasks`、`todayTasks`、`thisWeekTasks`、`nextWeekTasks`。
  - 同时从全量部门 OKR 结构派生可选 KR。
- 文件：`OrgView.tsx`
- 已确认实现：
  - 部门树通过递归 `renderDeptCard()` 全量渲染。
  - 搜索依赖递归 `matchesSearch()`，角色集合依赖递归 `globalRoles`。
  - 页面顶部、树节点、角色分配等都在同一组件内。
- 全仓排查结果：
  - 未发现 `react-window`、`react-virtual`、`virtualized`、分页组件、无限滚动实现。
- 影响：
  - 当任务、部门、用户规模扩大后，列表滚动、筛选、弹窗打开和输入反馈都会明显变慢。
- 最新复查结果：
  - `TaskCenterView.tsx`、`WorkbenchView.tsx`、`OrgView.tsx` 当前依然维持该模式。
  - 未发现引入虚拟滚动、分页或按需展开的新增实现。

### 5. 当前体验文案和交互状态存在少量不一致，影响“感知性能”

- 文件：`AppRoutes.tsx`
  - 只存在一个全屏初始化 loading，缺少按页面局部 skeleton / progressive loading。
- 文件：`OrgView.tsx`
  - 仍存在“创建后将自动保存”的历史文案，但项目当前已切换为手动保存。
- 文件：`MainLayout.tsx`
  - 头部会订阅 `isDirty/isSaving/showSaveSuccess/backendError/systemRoles`，这些全局状态变更会推动布局层刷新。
  - `handleNavigation()` 中对脏态的注释显示“未来可能弹 modal”，当前交互仍较粗。
- 影响：
  - 用户感知上会把“整屏等待”“无骨架占位”“提示文案不一致”理解为系统慢或不稳定。
- 最新复查结果：
  - `UnsavedChangesGuard.tsx` 已补充，这是体验改进项。
  - 但 `OrgView.tsx` 仍保留“创建后将自动保存”的历史文案，与当前手动保存模式不一致。
  - 说明近期更新修复了数据安全体验，但尚未统一性能感知和交互文案。

### 5.1 已改善但不等于加载性能问题已解决

- 已确认近期做过的改动：
  - 自动保存已切为手动保存。
  - realtime 冲突提示已收敛。
  - 未保存离开提醒已补充。
- 这些改动的价值：
  - 提升了稳定性和数据安全感知。
  - 降低了输入过程的误报和无意义同步。
- 但这些改动**不等同于**：
  - 首屏更快
  - 路由首包更小
  - 大列表滚动更流畅
  - 页面切换更轻
  - 大页面重渲染更少

### 6. 对于 React + Supabase 系统，更推荐的模式不是“登录后全量工作空间”

- 结合当前仓库形态，最佳实践应更接近：
  - 路由级代码分割
  - 页面级数据按需加载
  - 大列表分页 / 游标加载
  - 大树结构按需展开
  - 共享元数据小表可预取，重数据表按页面进入时查询
  - Zustand 只存会话级/跨页共享状态，不承载所有页面数据的唯一真源
  - 页面加载优先“先可用，再补全”，而不是等待整包 workspace

## 手动保存下 Realtime 评估

### 当前是否还需要前端 realtime 订阅

- 结论：**当前这个 OKR 系统在“手动保存 + 乐观锁冲突拦截”模式下，前端 realtime 订阅不是必需能力。**
- 原因：
  - 当前系统已经不再追求“输入中协同同步”。
  - 当前系统没有完整的多人实时协同编辑 UI，例如：
    - 远端变更高亮
    - 实时 presence
    - 实时合并/覆盖选择
    - 基于冲突差异的交互式合并
  - 真正的数据安全依赖的是：
    - `row_version` 乐观锁
    - 手动保存时的冲突拦截
  - 在这种前提下，realtime 的收益只剩：
    - 其它人改完后，本地界面能更快看到变化
  - 但它的代价是：
    - 增加订阅连接与事件处理开销
    - 增加本地脏态与远端回显协调复杂度
    - 增加误报、状态竞争和维护成本

### 移除 realtime 后会失去什么

- 其它用户修改后，本地页面不会自动刷新到最新结果。
- 用户、部门、流程、战略、业务定义的远端变化，需要：
  - 手动刷新页面
  - 重新登录
  - 或未来补一个显式“刷新数据”按钮
- 但不会失去的关键能力：
  - 手动保存
  - 乐观锁冲突拦截
  - 数据不被静默覆盖

### 移除 realtime 的影响范围

- 前端直接影响：
  - `App.tsx`
  - `useRealtimeSync.ts`
  - `hooks/useAppActions.ts`
  - `syncConflictGuard.ts`
  - `utils/taskSyncState.js`
- 数据库/脚本影响：
  - `sql/00_one_click_schema.sql` 中的 realtime publication 配置应移除或改为清理 publication 绑定
- 交互层影响：
  - 不再自动接收他人刚保存的结果
  - 冲突暴露时机统一为“点击保存时”
- 运维/性能影响：
  - 降低 websocket / subscription 开销
  - 降低前端运行时事件处理与重算频率

### 推荐决策

- 对当前项目，推荐：
  - **移除前端 realtime 订阅**
  - 保留乐观锁
  - 后续补一个显式“刷新最新数据”入口
- 不推荐继续保留当前这套 realtime：
  - 因为它不是完整实时协作方案
  - 但会持续拉高复杂度与维护成本
