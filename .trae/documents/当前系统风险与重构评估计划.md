# 当前系统风险与重构评估计划

## Summary

- 目标：全面分析当前仓库 `d:\aixing\okr-ai` 仍然存在的系统性风险，判断是否需要重构，以及最严重的问题应如何排序处理。
- 结论：**需要重构，但不建议推倒重写。** 当前更适合做“按优先级的定向重构”，先收口数据一致性与状态管理风险，再处理数据模型和性能结构问题。
- 总体判断：
  - 数据安全方向相比早期已经明显改善，手动保存、乐观锁、未保存离开提醒都已落地。
  - 但架构层仍有明显风险：**全局大 store、页面整棵订阅、超大 `useAppActions`、多表顺序提交导致中间态、核心业务结构仍大量依赖 JSONB blob。**
  - 当前最严重的问题不是某一个页面 bug，而是“**状态管理过粗 + 保存编排过重 + 数据模型过于 blob 化**”这三类风险叠加。

### 最新校正

- 截至当前代码状态，文档里的“**业务安全最高优先级**”判断仍然成立：`useAppActions.ts` 的跨域顺序保存中间态风险仍是系统性第一风险。
- 但文档对“**当前用户感知最高优先级**”描述不足：登录后进入 `/workbench` 时，虽然已经去掉了 `departments + strategy` 的首屏阻塞，但仍会加载**全量 `tasks`**，这会让“页面数据加载中...”在任务量大时持续十几秒。
- 因此当前执行顺序应调整为：
  1. 先解决 `/workbench` 的全量任务加载，恢复可用性与进入速度
  2. 再继续按原文档 P0 处理跨域保存中间态风险

## Current State Analysis

### 1. 最高优先级风险：页面级批量保存仍可能出现“部分成功、部分失败”的中间态

- 关键文件：
  - `d:\aixing\okr-ai\hooks\useAppActions.ts`
  - `d:\aixing\okr-ai\data.ts`
- 现状：
  - `handleSave()` 里按顺序保存 `strategy -> aiSettings -> processes -> departments -> users -> systemRoles -> businesses`。
  - 每一类数据又继续做删除、更新、新增，且跨域之间没有事务边界。
  - 例如部门、用户、角色、业务定义任何一步失败，前面已成功写入的数据不会自动回滚。
- 风险：
  - 会出现“前半段已经落库、后半段失败”的中间态。
  - 用户只看到统一的“保存失败”，但数据库可能已经部分变更。
  - 这类问题在多人协作、网络抖动、权限边界异常时风险最高。
- 判断：
  - 这是当前最严重、最需要优先治理的系统性问题。
  - 现有乐观锁只解决“单表冲突覆盖”，**没有解决跨域批量保存的原子性问题**。

### 2. 高优先级风险：全局状态仍然过粗，几乎所有主页面都整棵订阅 `useAppStore()`

- 关键文件：
  - `d:\aixing\okr-ai\store\useAppStore.ts`
  - `d:\aixing\okr-ai\components\WorkbenchView.tsx`

  - 以及其它多个主页面
- 现状：
  - `useAppStore.ts` 同时承载 `processes/departments/strategy/users/tasks/businesses/systemRoles/aiSettings` 和 `isDirty/isSaving/showSaveSuccess/backendError/currentProcessId/domainLoadStatus/...`。
  - 仓库中大量页面直接写 `const state = useAppStore()`，而不是按 selector 精确订阅。
- 风险：
  - 任何全局字段变化都可能推动大页面整体重渲染。
  - 手动保存成功提示、脏态变更、任务数组变更，都可能影响与当前页面无关的渲染。
  - 页面规模继续扩大后，性能、排查复杂度、误联动风险会一起上升。
- 判断：

### 3. 高优先级风险：`useAppActions.ts` 已成为超大编排中心，职责明显过载

- 关键文件：
  - `d:\aixing\okr-ai\hooks\useAppActions.ts`
- 现状：
  - 同一个 hook 同时负责：
    - 页面统一保存
    - 任务 optimistic update / 回滚
    - 流程增删改发布回滚
    - 系统设置提交
    - 部门 patch/rebase
    - 用户、角色、业务定义批量保存
  - 文件内部大量 `any`、跨域引用和全局状态写入。
- 风险：
  - 一个域的修改容易影响其它域保存行为。
  - 维护时很难建立清晰边界，回归成本高。
  - 新需求继续叠加时，这里会成为“唯一总开关”，风险持续上升。
- 判断：
  - 这是当前最典型的“需要重构而不是继续堆逻辑”的文件。
  - 后续应拆成 `task actions / org actions / process actions / settings actions / page save coordinator`。

### 4. 高优先级风险：数据模型仍然高度 blob 化，限制并发、查询和后续扩展

- 关键文件：
  - `d:\aixing\okr-ai\sql\00_one_click_schema.sql`

  - 任何局部变更都更容易退化成“整 blob 覆盖”。
  - 后续做统计、权限透视、搜索、审计时成本会越来越高。

## Proposed Changes

### 零、体验级 P0：工作台改为“只加载当前用户相关任务”

  - 其它需要全量任务的页面继续按完整任务域加载。
- 为什么：
  - 先解决最直观、最阻断使用的问题，即登录后长时间 loading。
- 怎么做：
  - 新增 `getWorkbenchTasks(userId)`。

  - 验收标准：
    - 登录后进入工作台不再被全量任务阻塞。
    - 后续进入 `任务中心/执行/周报/复盘` 时仍能正常加载全量任务。
