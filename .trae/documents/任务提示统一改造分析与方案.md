# 任务提示统一改造分析与方案

## 1. 背景与问题描述

当前项目中的提示体系并不统一，至少同时存在以下三类：

1. 全局提示：`App.tsx` 中挂载的 `sonner` `Toaster`
2. 页面级提示：各业务页面内部通过 `notification` 状态自行渲染的提示框
3. 右上角状态提示：`MainLayout.tsx` 顶部区域展示的 `保存中 / 已保存 / 未保存 / backendError`

用户当前反馈的问题主要集中在以下场景：

- 创建任务弹窗打开后，如果校验失败，提示不是在当前弹窗或当前页面内闭环展示，而是走了全局提示
- 弹窗打开时页面存在遮罩和模糊层，全局提示会出现在遮罩关系不清晰的区域，体验上像“被遮住”或“浮在错误层级”
- 失败提示在切换左侧 tab 后仍可能继续显示，导致上下文已经变化，但旧提示还在
- 页面顶部右上角同时存在“已保存”和“未保存”类状态，用户容易理解为互相矛盾

这说明当前问题不是单一组件 bug，而是“提示系统职责不清、作用域不清、生命周期不清”的综合问题。

## 2. 现状分析

### 2.1 全局提示现状

- `App.tsx` 挂载了全局 `Toaster`
- `TaskModal.tsx` 在前端校验失败时直接调用 `toast.error(...)`
- `LoginView.tsx` 也直接调用了 `toast`

这类提示的特点是：

- 生命周期独立于当前页面和当前弹窗
- 切换 tab 或路由时不会自动跟随业务上下文清理
- 在弹窗场景中容易和遮罩层、焦点层级产生冲突

### 2.2 页面级提示现状

以下页面都存在各自实现的 `showNotification`：

- `TaskCenterView.tsx`
- `ExecutionView.tsx`
- `WeeklyView.tsx`
- `WorkbenchView.tsx`
- `ReviewView.tsx`

共同特点：

- 基于本地 `useState`
- 通过 `setTimeout(() => setNotification(null), 3000)` 自动消失
- 没有统一封装
- 没有在 tab 切换、筛选切换、弹窗关闭时主动清理

因此会出现：

- 提示文案和样式不统一
- 不同页面行为不一致
- 页面切换上下文后旧提示短时间残留

### 2.3 右上角状态现状

`MainLayout.tsx` 顶部右侧显示的是全局状态，而不仅仅是普通消息提示：

- `backendError`
- `isSaving`
- `showSaveSuccess`
- `isDirty`

这类信息本质上更接近“全局状态指示器”，而不是“操作完成反馈”。

现有逻辑下出现“已保存”和“未保存”同时出现，并不一定是单纯渲染 bug，更可能是：

- `showSaveSuccess` 仍处于 3 秒展示窗口
- 另一个域或当前页面又进入了 `isDirty = true`
- 两个状态都是合法状态，但没有做互斥设计

所以用户看到的是“语义冲突”，本质上是“全局状态与局部状态并列展示但没有统一规则”。

## 3. 根因判断

结合代码实现，当前问题的根因主要有四个：

### 3.1 提示作用域不统一

- 表单校验失败走全局 `toast`
- 保存失败走页面级 `notification`
- 保存状态走顶部全局状态条

同一种“失败”被拆成三套不同出口，用户自然会感到混乱。

### 3.2 弹窗场景缺少就近反馈原则

`TaskModal.tsx` 中已经有弹窗内联错误区块 `error`，但又额外调用了全局 `toast.error`。

这会导致：

- 一个错误产生两处提示
- 用户视线被拉出当前弹窗
- 弹窗遮罩存在时，全局提示不再是最佳反馈位置

### 3.3 页面提示生命周期未绑定上下文

各页面 `showNotification` 仅通过定时器自动消失，没有在以下场景清理：

- 左侧 tab 切换
- 页面筛选条件切换
- 弹窗重新打开
- 页面卸载或上下文重置

因此提示会跨上下文残留。

### 3.4 顶部右侧状态缺少优先级和互斥规则

`showSaveSuccess` 与 `isDirty` 同时可为真，导致：

- “刚保存成功”与“当前仍有未保存改动”并存
- 技术上可能成立，体验上却容易误解

## 4. 需求合理性评估

## 结论

这个需求是合理的，但建议做“有边界的统一”，而不是字面意义上把所有右上角内容都机械替换成 toast。

### 4.1 合理的部分

以下内容应该统一成“当前页面的 toast 或页面内提示”：

- 任务创建成功
- 任务创建失败
- 任务删除成功
- 任务删除失败
- 无权限查看这类一次性反馈
- 当前操作的校验失败或提交失败

原因：

- 这些信息是“瞬时结果反馈”
- 与当前页面或当前弹窗强绑定
- 不应跨页面、跨 tab 保留

### 4.2 不建议直接一刀切替换的部分

以下内容不建议简单改成 toast：

- `保存中`
- `未保存`
- 全局脏状态
- 长生命周期的同步状态

原因：

- 这类信息是“状态指示”，不是“事件反馈”
- 如果改成 toast，会从“持续可见”退化为“出现 3 秒就消失”
- 用户反而无法持续感知当前页面是否还有未保存数据

因此，更合理的目标应是：

1. 把“操作反馈”统一成页面内 toast
2. 保留必要的“状态指示”，但重构其展示规则，避免冲突

## 5. 推荐改造目标

建议把提示体系重新划分为两层：

### 5.1 第一层：页面级操作反馈

适用于：

- 成功
- 失败
- 警告
- 权限不足
- 删除结果
- 提交结果

特征：

- 仅在当前页面可见
- 离开页面或切换主要上下文时自动清理
- 不与弹窗遮罩层冲突

### 5.2 第二层：全局状态指示

适用于：

- 是否保存中
- 是否存在未保存改动
- 是否存在全局级后端错误

特征：

- 持续可见
- 语义稳定
- 有明确优先级与互斥规则

## 6. 解决方案设计

## 方案 A：最小改动方案

适合先快速止血。

### 改造内容

1. 移除 `TaskModal.tsx` 中的 `toast.error(...)`
2. 保留弹窗内部 `error` 区块作为校验失败的唯一出口
3. 在各页面保留现有 `showNotification`，但补充清理逻辑
4. 在 tab 切换、筛选切换、弹窗关闭时清空页面级 `notification`
5. 在 `MainLayout.tsx` 中让 `showSaveSuccess` 与 `isDirty` 互斥显示

### 优点

- 修改范围小
- 风险低
- 能快速解决“遮罩层模糊提示”和“切 tab 残留”问题

### 缺点

- 仍保留多套提示实现
- 后续维护成本依旧偏高

## 方案 B：推荐方案

适合作为本次正式改造方案。

### 改造内容

1. 新增统一页面提示能力，例如：
   - `components/PageToast.tsx`
   - `hooks/usePageToast.ts`
   - 或在每个主页面容器内接入统一 `PageToastHost`
2. 将以下页面的本地 `notification` 实现统一替换为同一套页面 toast：
   - `TaskCenterView.tsx`
   - `ExecutionView.tsx`
   - `WeeklyView.tsx`
   - `WorkbenchView.tsx`
   - `ReviewView.tsx`
3. `TaskModal.tsx` 中：
   - 校验错误仅显示弹窗内联错误
   - 不再调用全局 `toast.error`
4. 保存失败等异步结果：
   - 统一交由所在页面的 `page toast` 展示
5. 为页面 toast 增加自动清理机制：
   - 路由切换清理
   - 左侧 tab 切换清理
   - 关键筛选条件切换清理
   - 弹窗关闭时清理与弹窗相关的提示
6. 调整 `MainLayout.tsx` 顶部右侧状态规则：
   - `isSaving` 优先级最高
   - `backendError` 次高
   - `isDirty` 与 `showSaveSuccess` 互斥
   - 当 `isDirty` 为真时，不显示“已保存”

### 优点

- 提示职责清晰
- 用户体验一致
- 可同时解决当前两个核心问题：
  - 弹窗失败提示位置不合理
  - 提示跨 tab 残留

### 缺点

- 需要统一多个页面
- 需要梳理提示 API，实施量中等

## 方案 C：完全统一为单一全局 toast

不建议本次采用。

### 原因

- 会再次引入弹窗遮罩层级问题
- 提示仍可能跨页面残留
- 无法表达页面上下文
- 与用户“当前页面提示”的诉求相反

## 7. 推荐实现细则

### 7.1 任务弹窗

`TaskModal.tsx` 建议规则：

- 表单字段校验失败：仅弹窗内联提示
- AI 检查失败：仅弹窗内联提示
- 点击保存后的服务端失败：由父页面 page toast 提示

这样可以形成清晰分工：

- 当前表单填错了，看弹窗内部
- 提交到后端失败了，看当前页面 toast

### 7.2 页面 toast 行为规范

建议统一如下行为：

- 位置固定在当前页面容器内，而不是应用根节点
- 仅显示一条最新消息，后来的覆盖前面的
- 默认 2.5 至 3 秒自动关闭
- 页面主上下文变化时主动关闭
- 支持 `success / error / info / warning`

### 7.3 顶部右侧状态规则

建议明确以下优先级：

1. `isSaving` 时只显示“保存中”
2. `backendError` 有值时显示错误状态，但不与成功状态同时展示
3. `isDirty` 为真时显示“未保存”
4. 只有 `!isSaving && !backendError && !isDirty && showSaveSuccess` 时才显示“已保存”

这样可以避免“已保存”和“未保存”同时出现。

## 8. 实施范围建议

### 第一阶段：快速修复

- `TaskModal.tsx`
- `MainLayout.tsx`
- `TaskCenterView.tsx`
- `ExecutionView.tsx`
- `WeeklyView.tsx`

目标：

- 先解决任务弹窗失败提示不合理
- 先解决切 tab 后提示残留
- 先解决顶部右上角状态冲突

### 第二阶段：统一收口

- `WorkbenchView.tsx`
- `ReviewView.tsx`
- `LoginView.tsx`
- 其他后续存在提示逻辑的页面

目标：

- 统一 API
- 去除重复的 `showNotification` 实现
- 降低后续维护成本

## 9. 风险评估

### 低风险

- 移除 `TaskModal.tsx` 中的全局 `toast.error`
- 给页面通知增加清理逻辑
- 调整顶部状态显示优先级

### 中风险

- 抽象统一页面 toast 组件
- 批量替换多个页面的提示调用

### 关注点

- 不要误把“状态指示”全部改成“瞬时提示”
- 不要让弹窗内部错误和页面 toast 再次重复出现
- 要避免在多个页面各自维护一套不同文案与时序

## 10. 验收标准

改造完成后，至少应满足以下结果：

1. 创建任务弹窗内字段校验失败时，不再出现应用级全局提示
2. 弹窗打开时，失败信息不会出现在遮罩层语义不清的位置
3. 保存失败提示只在当前页面出现
4. 切换左侧 tab 或关键筛选后，旧提示不会继续残留
5. 顶部右侧不会同时出现“已保存”和“未保存”
6. 各任务相关页面的成功/失败提示风格一致

## 11. 最终建议

如果本次目标是既解决当前问题，又不给后续维护留下新债，建议采用“方案 B：推荐方案”。

简化后的决策建议如下：

- 同意你的需求方向
- 但不建议把“所有右上角内容”全部机械改成 toast
- 应该把“操作反馈”改成当前页面 toast
- 应该把“保存状态”保留为状态指示，并增加互斥规则
- 先从任务相关页面开始统一，再逐步扩展到全项目

如果需要进入实施阶段，建议下一步直接输出一份“具体改造清单”，按文件列出每个组件该怎么改。
