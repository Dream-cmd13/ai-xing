# 去除自动保存统一手动保存改造计划

## Summary

- 目标：去除当前项目中的自动保存、防抖保存、改即提交和局部立即保存，统一改为“先改本地状态，最后点击页面保存按钮才落库”。
- 用户已明确的决策：
  - 新增、编辑、删除全部纳入手动保存。
  - 保留弹窗里的提交按钮，不强行全部并入页面总保存。
- 预期收益：
  - 消除“自动保存回显”和“连续输入”带来的误报冲突。
  - 降低多人协作时由自动保存触发的写入交错。
  - 统一交互模型，所有页面都遵循“修改 -> 脏态提示 -> 手动保存”。
- 风险：
  - 改造面较大，不只是去掉 `debounce`，还要重构多个“操作即落库”的链路。
  - 必须补齐页面离开提醒、脏态提示和批量提交逻辑，否则用户会误以为已保存。

## Current State Analysis

### 1. 当前真正的自动保存集中在 3 条主链路

- `strategy` 自动保存：
  - 文件：`hooks/useAppActions.ts`
  - 实现：`debouncedSaveStrategy`
  - 触发：`handleSetStrategy(..., autoSave = true)`
- `processes` 自动保存：
  - 文件：`hooks/useAppActions.ts`
  - 实现：`debouncedSaveProcess`
  - 触发：`setProcessData`、`updateProcessProps`
- `departments` 自动保存：
  - 文件：`hooks/useAppActions.ts`
  - 实现：`debouncedSaveDepartments`
  - 触发：`handleSetDepartments(..., autoSave = true)`

### 2. 当前还有大量“改即提交”，并不属于防抖保存，但同样不符合目标

- `users`：
  - 文件：`hooks/useAppActions.ts`
  - 实现：`handleSetUsers` 直接走 `executeAtomicOperation`
- `systemRoles`：
  - 文件：`hooks/useAppActions.ts`
  - 实现：`handleSetSystemRoles` 直接提交
- `businesses`：
  - 文件：`hooks/useAppActions.ts`
  - 实现：`handleSetBusinesses` 直接提交
- `aiSettings`：
  - 文件：`hooks/useAppActions.ts`
  - 实现：`handleSetAISettings` 直接提交
- `tasks`：
  - 文件：`components/TaskCenterView.tsx`、`components/ExecutionView.tsx`、`components/WeeklyView.tsx`、`components/WorkbenchView.tsx`、`components/ReviewView.tsx`
  - 实现：任务新增/编辑/删除在页面或弹窗内直接落库

### 3. 当前已经存在页面级“保存按钮”，这是本次改造的有利条件

- 已有 `handleSave` 保存按钮的页面：
  - `components/OrgView.tsx`
  - `components/StrategyView.tsx`
  - `components/ProcessView.tsx`
  - `components/WorkbenchView.tsx`
  - `components/WeeklyView.tsx`
  - `components/ExecutionView.tsx`
  - `components/TaskCenterView.tsx`
  - `components/BusinessDefinitionView.tsx`
  - `components/UserView.tsx`
  - `components/MenuPermissionView.tsx`
- 说明：
  - UI 层已经有统一保存按钮骨架。
  - 但底层 `handleSave` 当前只真正处理 `strategy / aiSettings / dirty processes / departments`，并没有统一接管所有域。

### 4. 当前“页面保存”与“局部立即保存”并存，需按场景收敛而不是一刀切

- 例如任务模块：
  - 页面上有“保存”按钮；
  - 但任务弹窗内又会直接 `addTask / updateTask / deleteTask`。
- 例如系统设置：
  - `components/SystemConfigView.tsx` 中 `handleSaveConfig` 会先调用 `setAISettings`，再调用 `handleSave`；
  - 实际是“双通路”，既局部提交又页面提交。
- 这类结构如果要统一成“去除自动保存”，必须区分：
  - 页面编辑型场景：改为页面手动保存；
  - 弹窗表单型场景：允许保留弹窗内提交按钮；
  - 但无论哪种，都不能继续“输入中自动保存”或“无感立即保存”。

### 5. 该需求总体合理，但需要对个别模块特殊对待

- 合理的部分：
  - 可以显著减少因自动保存导致的误报冲突；
  - 更符合复杂表单、树结构、流程图、OKR 编辑这类“先改一批再统一提交”的工作流；
  - 在多人协作下更容易把冲突暴露在“点击保存”时，而不是输入过程。
- 需要特殊对待的部分：
  - 任务模块：原本按单条任务原子保存，改成页面级统一提交后，必须设计“新增/编辑/删除任务的本地暂存 + 批量提交”。
  - 流程模块：拖拽节点、连线频繁变动，改为手动保存后，要保证画布修改只更新本地，不再触发任何落库。
  - 系统设置：当前只有局部保存入口，没有页面总保存语义，需要决定挂到哪个统一保存入口。
  - 删除操作：以前删完即落库，改为手动保存后，需要给出“待删除”视觉状态，否则用户会误以为已经真实删除。

## Proposed Changes

### 方案结论

- 推荐采纳“页面编辑型场景统一手动保存 + 弹窗表单保留显式提交按钮”的方案。
- 不保留自动保存，但允许保留有明确按钮触发的局部提交。
- 原因：
  - 用户已明确希望弹窗仍可提交；
  - 自动保存才是本轮重点问题，显式点击按钮提交不属于自动保存；
  - 弹窗表单天然适合“填完立即提交”，强行并入页面总保存反而会增加交互成本和遗漏风险。

### 改造原则

- 原则 1：所有 setter 只改 store，不直接调用 data API。
- 原则 2：页面内连续编辑先落本地状态，并标记脏态。
- 原则 3：页面主表单、流程画布、组织树、OKR 编辑等复杂编辑区，统一通过页面保存按钮提交。
- 原则 4：弹窗型表单允许保留“提交/保存”按钮，但必须是显式点击触发，不能自动保存。
- 原则 4：所有页面离开前，如果存在未保存修改，必须提示。
- 原则 5：删除改为“本地待删除”还是“弹窗确认后立即提交”，取决于该操作属于页面编辑流还是弹窗提交流，但都不能无按钮自动落库。

### 一、重构 `hooks/useAppActions.ts`

- 文件：`hooks/useAppActions.ts`
- 目标：把它从“保存器 + 自动保存器 + 原子提交器混合体”改成“本地状态编排器 + 手动提交器”。
- 具体改动：
  - 删除 `debouncedSaveStrategy`
  - 删除 `debouncedSaveProcess`
  - 删除 `debouncedSaveDepartments`
  - 删除对 `lodash/debounce` 的依赖
  - 删除或废弃 `saveSuccessTimeoutRef` / `savingTimeoutRef` 中与自动保存绑定的部分
  - 让以下方法只改本地，不落库：
    - `handleSetDepartments`
    - `handleSetUsers`
    - `handleSetSystemRoles`
    - `handleSetAISettings`
    - `handleSetBusinesses`
    - `setProcessData`
    - `updateProcessProps`
    - `handleSetTasks`
    - `handleSetStrategy`
  - 停止在这些方法里调用：
    - `executeAtomicOperation`
    - `saveStateDirectly`
    - `addDb* / updateDb* / deleteDb*`
- 新的职责划分：
  - `handleSave` 成为唯一统一落库入口
  - 各 `handleSet*` 仅负责：
    - 更新 store
    - 标记 `isDirty`
    - 记录新增/修改/删除队列

### 二、为页面编辑型实体建立“待提交变更集”

- 文件：
  - `store/useAppStore.ts`
  - `types.ts`
  - `hooks/useAppActions.ts`
- 目标：支持“页面内编辑很多次，最后一次性提交”
- 推荐新增的 store 状态：
  - `pendingDeletedProcessIds: string[]`
  - `pendingDeletedDepartmentIds: string[]`
  - `pendingDeletedUserIds: string[]`
  - `pendingDeletedSystemRoleIds: string[]`
  - `pendingDeletedBusinessIds: string[]`
  - `pendingDeletedTaskIds: string[]`
- 可选增强：
  - 对任务增加 `pendingTaskOps`，显式区分 `create/update/delete`
  - 对用户、角色、业务、部门也可以记录 op 类型，而不是只靠 `lastSaved* vs current*` diff
- 为什么要做：
  - 对页面编辑型场景，手动保存模式下不能靠“修改即落库”
  - 必须有一套“待删除但未提交”的本地状态表达
  - 但弹窗型表单不一定全部依赖这套机制，可在按钮点击时直接提交

### 三、扩展 `handleSave` 为页面级统一提交入口

- 文件：`hooks/useAppActions.ts`
- 当前 `handleSave` 只处理：
  - `strategy`
  - `aiSettings`
  - `dirty processes`
  - `departments`
- 改造后 `handleSave` 需要统一处理的页面编辑型域：
  - `strategy`
  - `aiSettings`
  - `processes`
  - `departments`
  - `users`
  - `systemRoles`
  - `businesses`
- `tasks` 视页面而定：
  - 页面内批量编辑的任务，纳入 `handleSave`
  - 弹窗内单条任务提交，允许继续通过弹窗按钮单独提交
- 提交顺序建议：
  1. `strategy`
  2. `aiSettings`
  3. `processes`
  4. `departments`
  5. `users`
  6. `systemRoles`
  7. `businesses`
  8. `tasks`
- 原因：
  - 先保存全局配置和组织主数据，再保存依赖其引用的数据；
  - 任务通常依赖部门、用户、战略、流程上下文，放最后更稳。
- 提交模式建议：
  - 仍保留当前乐观锁检查
  - 每个域按“删除 -> 新增 -> 更新”或“新增 -> 更新 -> 删除”统一设计，但要保持全域一致
  - 本轮不要求立刻做后端事务化，但接口编排必须清晰

### 四、页面层统一改为“编辑只改本地，按钮统一提交”

#### 1. 组织页 `components/OrgView.tsx`

- 现状：
  - 页面已有保存按钮；
  - 通过 `setDepartments` 进入自动保存链。
- 改造：
  - 保留页面保存按钮
  - 所有树编辑、岗位编辑、部门字段编辑都只改本地
  - 删除自动保存依赖
- 特殊点：
  - 删除部门要有“待删除”表现，不能点完就当已提交

#### 2. OKR 页 `components/StrategyView.tsx`

- 现状：
  - `strategy` 与 `departments` 混合编辑
  - `setStrategy` 和 `setDepartments` 会触发自动保存
- 改造：
  - 所有战略文本、公司 OKR、部门 OKR 编辑只改本地
  - 最终统一点击页面保存按钮提交
- 特殊点：
  - 这是一个跨域页面，保存时可能同时触发 `strategy + departments`
  - 保存按钮需明确提示“保存战略与部门 OKR”

#### 3. 流程页 `components/ProcessView.tsx`

- 现状：
  - 流程节点拖拽、属性修改会走 `setProcessData` / `updateProcessProps`，当前会自动保存
- 改造：
  - 拖拽、编辑、发布前普通修改都只改本地
  - 保存按钮统一提交
- 特殊点：
  - `publishProcess`、`rollbackProcess` 当前是立即落库
  - 需要改成本地状态变更，最终由页面保存提交
  - 如果产品上认为“发布版本”必须立即生效，则这是唯一需要再次确认的潜在例外；当前按用户决策，仍统一纳入手动保存

#### 4. 任务相关页面

- 涉及文件：
  - `components/WorkbenchView.tsx`
  - `components/WeeklyView.tsx`
  - `components/ExecutionView.tsx`
  - `components/TaskCenterView.tsx`
  - `components/ReviewView.tsx`
  - `components/TaskModal.tsx`
- 现状：
  - 任务在弹窗内经常直接 `addTask / updateTask / deleteTask`
  - 页面又同时存在 `handleSave` 按钮
- 改造：
  - 保留任务弹窗内的“保存/提交”按钮
  - 弹窗按钮点击后允许直接提交单条任务
  - 页面内列表级、批量级编辑仍改为手动保存
  - 页面总保存按钮继续负责页面级脏数据提交
- 这是本次改造最需要特殊对待的部分：
  - 任务模块横跨多个页面
  - 同一条任务可能在不同页面以不同视图编辑
  - 需要拆分为两类流：
    - 弹窗单条任务流：显式按钮提交
    - 页面批量任务流：页面按钮提交

#### 5. 用户页与权限页

- 涉及文件：
  - `components/UserView.tsx`
  - `components/MenuPermissionView.tsx`
- 现状：
  - 列表编辑后通常立即提交
- 改造：
  - 全部改成本地变更
  - 页面保存按钮统一提交
- 特殊点：
  - 批量导入用户属于高影响操作，若导入后不立即保存，页面要有非常明确的“待保存”提示

#### 6. 事业定义页

- 文件：`components/BusinessDefinitionView.tsx`
- 改造：
  - 所有事业项新增、编辑、删除只改本地
  - 页面保存按钮统一提交

#### 7. 系统设置页

- 文件：`components/SystemConfigView.tsx`
- 现状：
  - `handleSaveConfig` 先局部保存，再调用全局保存
- 改造：
  - 保留显式按钮触发保存
  - 去掉“点一次按钮走两条提交流程”的双通路
  - 收敛成单一显式提交入口
- 特殊点：
  - 系统设置更接近弹窗/表单提交型场景，不适合强行并入其他页面总保存
  - 重点是保留按钮，但取消自动保存和双重提交

### 五、收敛 `saveStateDirectly` 与 `executeAtomicOperation`

- 文件：`hooks/useAppActions.ts`
- 处理建议：
  - `saveStateDirectly`：
    - 目标是缩小使用范围
    - 不再作为页面编辑的通用回退路径
    - 只保留给明确的显式按钮提交场景，或进一步替换成更清晰的单实体提交方法
  - `executeAtomicOperation`：
    - 不再用于“无按钮的改即提交”
    - 可保留给弹窗按钮提交、系统设置按钮提交这类显式操作

### 六、调整 Realtime 与冲突提示策略

- 文件：
  - `useRealtimeSync.ts`
  - `syncConflictGuard.ts`
- 改造目标：
  - 去除自动保存后，realtime 不再需要服务“输入中自动回显”
  - 要转而服务“本地有未保存修改时的远端变更提醒”
- 新策略：
  - 本地无脏数据：正常接收远端变更并更新界面
  - 本地有脏数据：
    - 不直接覆盖本地
    - 标记“远端已更新”
    - 用户保存时再做冲突检查
- 这会比当前实现更简单，也更符合手动保存模型

### 七、补齐 UX：脏态、离开提醒、待删除提示

- 文件范围：
  - `App.tsx`
  - 各主页面组件
- 必做交互：
  - 明确的“未保存修改”提示
  - 页面关闭/路由切换前提醒
  - 保存按钮禁用态、保存中态、保存成功态
  - 删除后视觉标记“待删除，尚未保存”
- 否则：
  - 用户会误以为点过删除就已落库
  - 或误以为改完已经自动保存

## Assumptions & Decisions

- 决策 1：自动保存全部去除，但显式点击按钮触发的提交允许保留。
- 决策 2：页面级复杂编辑统一走页面保存按钮；弹窗型表单允许保留弹窗提交按钮。
- 决策 3：本轮目标是“去掉无感自动保存与改即提交”，不是“去掉所有局部提交按钮”。
- 决策 4：现有页面保存按钮继续保留，并作为页面编辑型场景的主要持久化入口。
- 假设：用户接受页面编辑型删除操作“先本地待删除、后统一提交”的交互变化。
- 假设：任务模块允许同时存在“弹窗单条提交”和“页面批量提交”两种模式，但需严格区分。
- 假设：本轮先维持现有 data API 形态，通过前端编排完成统一手动保存，而不是立刻引入后端事务接口。

## Verification Steps

- 代码层核验：
  - `hooks/useAppActions.ts` 中不再存在 `debouncedSaveStrategy`
  - `hooks/useAppActions.ts` 中不再存在 `debouncedSaveProcess`
  - `hooks/useAppActions.ts` 中不再存在 `debouncedSaveDepartments`
  - 各 `handleSet*`、`setProcessData`、`updateProcessProps` 不再直接落库
  - `saveStateDirectly` 不再被业务页面调用
  - `executeAtomicOperation` 不再被业务编辑场景直接调用
- 页面层核验：
  - 组织、OKR、流程、事业、用户、权限、系统设置、任务相关页面，修改后不会自动保存
  - 关闭页面或切换路由时，有未保存提醒
  - 点击页面保存按钮或弹窗提交按钮后才真正写数据库
- 行为核验：
  - 单人连续快速输入不再触发冲突提示
  - 两个用户分别修改不同记录，在未点击保存前不会互相干扰
  - 两个用户修改同一记录，冲突暴露在点击保存时，而不是输入时
  - 删除操作在点击保存前只是本地待删除，不会真实消失于数据库
- 特殊场景核验：
  - 任务弹窗保留提交按钮，点击后可正常提交单条任务
  - 系统设置保留按钮提交，但不再双重提交
  - 流程发布/回滚在未点击总保存前不写库
