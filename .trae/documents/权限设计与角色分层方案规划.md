# 权限设计与角色分层方案规划

## Summary

- 目标：基于当前仓库 `d:\aixing\okr-ai` 的真实权限实现，评估“仅管理员 + 普通用户”是否足够，并产出一套符合真实组织场景的权限设计方案。
- 本次已确认的真实业务规则：
  - 角色层级倾向：`管理员 / 部门长 / 普通员工`
  - 总经理：等同管理员，不单独建模
  - 部门长：可查看全公司数据，但写权限只限本部门数据
  - 普通员工：只能看本部门数据；跨部门任务中，只要自己参与也能看
  - 普通员工：可创建自己需要的数据，并且只能修改/删除自己创建的数据
  - 普通员工创建边界：默认只能创建本部门数据；任务允许因为参与关系形成跨部门协作
- 总结论：
  - **当前仅 `Admin | User` 两层角色不够。**
  - 但也**不建议直接扩成很多业务角色散落在前后端各处**。
  - 最合适的方案是：
    - 保留“系统级身份”最小核心枚举
    - 补一层“业务访问范围角色”
    - 再用 RLS 做强约束，前端权限仅做体验控制

## Current State Analysis

### 1. 当前角色模型过粗，只支持 `Admin | User`

- 关键文件：
  - `d:\aixing\okr-ai\types.ts`
- 现状：
  - `User.role` 当前只有 `'Admin' | 'User'`，见 `types.ts`
  - 这意味着：
    - “普通员工”和“部门长”在系统层被视为同一种用户
    - 总经理如果不等同 Admin，就完全没有位置表达
- 问题：
  - 无法表达“可见范围”和“写权限范围”的差异
  - 当前业务里最重要的权限差别并不是“能不能进某页面”，而是“能看哪些数据、能改哪些数据”

### 2. 当前前端权限模型偏菜单化，不足以表达数据范围

- 关键文件：
  - `d:\aixing\okr-ai\hooks\usePermissions.ts`
  - `d:\aixing\okr-ai\utils\permissions.ts`
  - `d:\aixing\okr-ai\components\MenuPermissionView.tsx`
- 现状：
  - 前端当前通过 `systemRoleIds`、`customPermissions`、`padPermissions` 做菜单按钮级控制
  - `hasPermission()` 关注的是 `view/create/update`
  - `canViewTask()` 已经引入了一部分“部门 + 参与关系”的逻辑
- 问题：
  - 现有模型主要解决“UI 是否展示”
  - 但真实权限核心是：
    - 数据范围：能看到哪些部门、哪些任务、哪些流程、哪些 OKR
    - 写入边界：能改本部门还是只能改自己创建
  - 这些规则现在没有统一的角色语义，逻辑分散在前端工具函数中

### 3. 当前数据库 RLS 仍然基本以“管理员 / 非管理员”两层思维编写

- 关键文件：
  - `d:\aixing\okr-ai\sql\00_one_click_schema.sql`
- 现状：
  - `users/departments/processes/strategy/businesses/tasks/system_roles/settings` 多数 SELECT 仍是 `USING (true)`
  - 更新/删除多数是“仅管理员”或“本人/owner/管理员”
  - `tasks_update` 当前仅允许 `owner_id = current_user_id()` 或管理员
- 问题：
  - 这与已确认的真实业务规则明显不匹配：
    - 部门长应可看全公司，但不是管理员
    - 部门长应可管理本部门数据，但不是全局管理员
    - 普通员工应只能看本部门 + 自己参与任务
    - 普通员工对非自己创建的数据不应有写权限
  - 当前 RLS 既过宽，又表达不了“部门长”这种中间角色

### 4. 当前“管理员 + 普通用户”是否足够：结论是不够

- 原因 1：
  - 你真实业务里已经存在“部门长”和“普通员工”的稳定差异，这不是临时特例
- 原因 2：
  - 如果继续只保留 `Admin | User`，那部门长能力只能靠 `padPermissions/systemRole/customPermissions` 拼出来
  - 这样会导致权限来源混乱，前后端都很难审计
- 原因 3：
  - 当前最关键的不是“菜单权限多几项”，而是“数据访问范围”与“数据写入边界”
  - 两层角色不利于设计一致的 RLS

## 已确认的业务规则

### 1. 角色层级

- 推荐最终角色分层：
  - `管理员`
  - `部门长`
  - `普通员工`
- 其中：
  - 总经理 = 管理员
  - 不单独再拆“总经理角色”

### 2. 数据可见范围

- 管理员：
  - 可看全公司所有数据
- 部门长：
  - 可看全公司所有数据
- 普通员工：
  - 可看本部门数据
  - 对于任务，只要自己是负责人、参与人、审批人，即使跨部门也可以看

### 3. 数据写入边界

- 管理员：
  - 全量可管
- 部门长：
  - 只能修改和删除本部门数据
  - 不应天然拥有全局修改权
- 普通员工：
  - 允许创建数据
  - 只能修改和删除自己创建的数据
  - 创建默认应绑定本部门；仅任务允许因参与协作产生跨部门可见关系

### 4. 普通员工创建边界的最终口径

- 已确认规则：
  - 普通员工不是“只要自己创建就可以任意跨部门建数据”
  - 正确口径是：
    - 默认只能创建本部门数据
    - 任务是例外，可以因参与关系跨部门协作
- 这意味着：
  - 普通员工不应创建公司级战略、全局业务定义、系统角色、系统设置
  - 普通员工也不应创建不属于本部门的流程和 OKR
  - 普通员工若发起任务，任务应默认绑定自己的部门；后续可邀请跨部门参与人/审批人

## Proposed Changes

### 一、角色模型设计：改成“三层业务角色 + 系统权限扩展”

- 涉及文件：
  - `d:\aixing\okr-ai\types.ts`
  - `d:\aixing\okr-ai\data.ts`
  - `d:\aixing\okr-ai\sql\00_one_click_schema.sql`
- 建议：
  - 将 `User.role` 从当前 `'Admin' | 'User'` 扩展为显式业务角色枚举，例如：
    - `Admin`
    - `Manager`
    - `Employee`
- 为什么：
  - 你的真实业务差异主要体现在这三类身份
  - 这层角色应负责表达“默认数据范围”和“默认写权限边界”
- 决策：
  - 不把“总经理”单独作为新枚举
  - 总经理归入 `Admin`

### 二、权限设计拆成三层，不再混用

#### 1. 第一层：业务角色默认规则

- 负责回答：
  - 能看哪些数据
  - 能改哪些数据
- 规则建议：
  - `Admin`：
    - 全量查看
    - 全量新增/修改/删除
  - `Manager`：
    - 全量查看
    - 仅能修改/删除本部门数据
  - `Employee`：
    - 查看本部门数据
    - 查看自己参与的跨部门任务
    - 仅能修改/删除自己创建的数据

#### 2. 第二层：菜单/模块权限

- 保留现有 `systemRoles` 与 `customPermissions`
- 但角色职责要收窄：
  - 只负责“是否开放某模块入口、某类功能按钮”
  - 不再承担核心数据范围定义
- 例如：
  - 某员工即使理论上能看本部门数据，如果没有对应模块 view 权限，前端仍可隐藏入口
- 但数据库侧是否允许访问，仍必须由 RLS 决定

#### 3. 第三层：数据库 RLS 强约束

- 所有最终安全边界以 RLS 为准
- 前端只做体验与引导，不做安全假设

### 三、资源维度权限方案

#### 1. `users`

- 可见建议：
  - `Admin`、`Manager`：可查看全员
  - `Employee`：建议只看本部门成员的最小字段视图
- 写入建议：
  - `Admin`：可增删改
  - `Manager`：不建议直接管理 `users` 主表账户与系统角色
  - `Employee`：仅可修改本人资料中的有限字段，不能改角色和权限字段
- 说明：
  - 用户账号、角色、权限是系统管理对象，不应下放给部门长

#### 2. `departments`

- 可见建议：
  - `Admin`、`Manager`：可看全量部门树
  - `Employee`：只看本部门分支，或至少只看本部门节点及必要祖先
- 写入建议：
  - `Admin`：全量可改
  - `Manager`：仅可改自己负责的部门范围
  - `Employee`：不应直接改部门结构
- 关键建议：
  - 当前表里没有“部门负责人用户 ID”字段，只有 `manager_name`
  - 若要让部门长权限可靠落地，建议后续引入结构化负责人标识，例如 `manager_user_id`

#### 3. `processes`

- 可见建议：
  - `Admin`、`Manager`：可看全量流程
  - `Employee`：只看本部门流程，或与本部门强关联的流程
- 写入建议：
  - `Admin`：全量可改
  - `Manager`：只能改本部门所属流程
  - `Employee`：只能改自己创建的流程
- 风险提示：
  - 当前 `processes` 表没有明确 `department_id/created_by`
  - 若没有结构化归属字段，RLS 无法可靠判断“本部门”和“自己创建”
- 结构结论：
  - **需要改表结构**
  - 最少应补：
    - `department_id`
    - `created_by`

#### 4. `strategy / okr`

- 可见建议：
  - `Admin`、`Manager`：可看全量
  - `Employee`：只看本部门 OKR + 必要的公司级目标映射
- 写入建议：
  - `Admin`：可全量改
  - `Manager`：只能改本部门 OKR
  - `Employee`：只能改自己创建的业务项或填写输入，不应直接全量改部门 OKR
- 风险提示：
  - 当前 OKR 混在 `departments.okrs` 与 `strategy.company_okrs` JSONB 中
  - 这会让精确 RLS 极难表达
- 结构结论：
  - **需要重构，且不是小修字段就能彻底解决**
  - 对员工/部门长权限要真正落地，至少要满足其一：
    - 方案 A：把部门 OKR 从 `departments.okrs` 中拆出结构化表，并带 `department_id/created_by`
    - 方案 B：短期内禁止普通员工直接创建/编辑 OKR，仅允许填写与自己相关的输入
- 推荐判断：
  - 如果近期要快速落地权限，先走 **方案 B**
  - 如果中期要做可维护的精细权限，必须走 **方案 A**

#### 5. `tasks`

- 可见建议：
  - `Admin`：全量可看
  - `Manager`：全量可看
  - `Employee`：
    - 可看本部门任务
    - 可看自己负责/参与/审批的跨部门任务
- 写入建议：
  - `Admin`：全量可改
  - `Manager`：可改本部门任务
  - `Employee`：只能改删自己创建的任务
- 关键结论：
  - `tasks` 是最适合优先做精细 RLS 的域
  - 因为它已经有 `department_id`、`owner_id`、`participant_ids`、`approver_ids`
- 但仍缺口：
  - 当前并没有显式 `created_by`
  - 如果“创建者”不等于 `owner_id`，则还需要补字段
- 结构结论：
  - **建议改表，但不是绝对阻塞**
  - 如果你认可“创建者 = owner”，短期可先用 `owner_id` 充当创建者语义
  - 如果你要精确表达“创建者、负责人、参与人、审批人”四者不同，建议补：
    - `created_by`

#### 6. `businesses / system_roles / settings`

- 建议：
  - 仅 `Admin` 可见和可改
  - `Manager`、`Employee` 不应直接访问
- 原因：
  - 这些属于系统治理与企业定义层，不是普通业务执行层
- 结构结论：
  - 当前不需要为普通员工/部门长权限而改这几张表
  - 只需在 RLS 中明确收紧到管理员可见即可

### 四点五、是否需要修改表结构：明确结论

#### 结论：需要，但不是所有表都同优先级

- 必须优先改的：
  - `processes`
  - `tasks`（建议补）
- 中长期必须重构的：
  - `departments.okrs`
  - `strategy.company_okrs`
- 暂时不必因本次权限设计而改的：
  - `system_roles`
  - `settings`
  - `businesses`

#### 为什么必须改

- 因为你现在要表达的是三类核心规则：
  - 是否属于本部门
  - 是否是自己创建
  - 是否因任务参与关系获得可见权
- 当前多数表并没有可靠字段支持这三类判断
- 没有结构化归属字段，RLS 只能写成脆弱的特例逻辑，后续很难维护

#### 最小必要字段建议

- `tasks`
  - 建议新增：`created_by`
- `processes`
  - 建议新增：`department_id`, `created_by`
- `departments`
  - 建议新增：`manager_user_id`
- `okr` 相关
  - 若进入结构化重构，建议独立表至少带：
    - `department_id`
    - `created_by`
    - `scope`（company / department / personal，可选）

### 五、是否三层角色就够：评估结论

#### 结论：对你当前真实业务，三层足够

- 原因 1：
  - 你已经明确总经理等同管理员，因此不需要单独再拆一层
- 原因 2：
  - 部门长和普通员工的主要差异，已经能被 `Manager` 与 `Employee` 准确表达
- 原因 3：
  - 额外复杂性应放在“资源归属字段 + RLS + 模块权限”上，而不是继续增加角色数量

#### 什么时候三层不够

- 当你未来出现以下场景时，才考虑第四层或更多层：
  - 总经理与系统管理员分离
  - 多个事业部负责人拥有跨部门但非全局权限
  - 审批链角色与组织角色强分离
  - 外部协作者/顾问需要受限账号

### 六、推荐的最终权限架构

- 系统角色主枚举：
  - `Admin`
  - `Manager`
  - `Employee`
- 数据权限主原则：
  - `Admin`: 全量可见、全量可写
  - `Manager`: 全量可见、本部门可写
  - `Employee`: 本部门可见、参与任务可见、仅自己创建可写
- 菜单权限：
  - 继续使用 `systemRoles + customPermissions`
  - 但只做功能入口补充控制
- 强约束：
  - 最终以 PostgreSQL RLS 实施

### 七、落地顺序建议

#### 第一阶段：先补权限模型必需字段

- 涉及文件：
  - `types.ts`
  - `sql/00_one_click_schema.sql`
  - `data.ts`
- 建议优先补齐：
  - `users.role` 扩展为三层角色
  - 为关键业务对象增加可靠归属字段：
    - `created_by`
    - `department_id`
    - 对部门增加负责人用户字段，例如 `manager_user_id`
  - 同时明确“员工创建默认属于本部门，任务允许参与式跨部门协作”的规则

#### 第二阶段：先做 `tasks` 的精细 RLS

- 原因：
  - 任务规则最清晰，且你已经明确“本部门 + 参与可见 + 自己创建可改删”
  - 这最适合作为权限模型试点

#### 第三阶段：再做 `departments / processes / okr`

- 原因：
  - 这几个域当前大量依赖 JSONB blob
  - 如果不先补归属字段或结构化拆分，RLS 会很脆弱

#### 第四阶段：最后收口菜单权限配置页

- 原因：
  - 先确定数据安全边界，再收 UI 权限体验

## 方案结论

- 你的真实业务场景下，**管理员 + 普通用户这两层不够**。
- 但也**不需要把总经理单独拆出来**，因为你已明确总经理等同管理员。
- 当前最合理的角色模型是：
  - `管理员`
  - `部门长`
  - `普通员工`
- 真正的权限设计不应只是页面按钮权限，而应拆成：
  - 业务角色默认规则
  - 菜单功能权限
  - 数据库 RLS 强约束
- 如果后续进入实施阶段，建议优先从 `tasks` 做试点，因为它最接近你已明确的业务规则，并且字段条件最接近可落地的 RLS。
- 关于是否要改表结构：
  - **需要改，而且重点不是为了“代码更漂亮”，而是为了让 RLS 能可靠判断“本部门”和“自己创建”。**
- 关于普通员工创建边界：
  - **应限制为默认只能创建本部门数据。**
  - **任务可例外支持跨部门协作，但应通过参与/审批关系开放可见，而不是允许员工随意创建跨部门业务对象。**
