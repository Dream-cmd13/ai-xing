# 并发保存模式分析计划

## Summary

- 目标：基于当前仓库 `d:\aixing\okr-ai`，分析是否存在与“自动延时全量保存”“删除后整批重建”相似的保存模式，判断多人同时修改时是否会出现并发覆盖、脏数据回写、失败后中间态不一致，并给出多种治理方案。
- 范围：仅分析当前仓库，不假设存在销售单据、报价单、销售订单、样品单、退货单等业务模块。
- 输出：现状分析、并发风险判断、与销售单据类模式的对应关系、多方案改造建议。

## Current State Analysis

### 1. 仓库业务形态与用户描述不完全一致

- 当前仓库是 OKR / 流程 / 组织 / 任务系统，核心目录集中在 `components/`、`hooks/`、`data.ts`、`useRealtimeSync.ts`、`store/useAppStore.ts`。
- 未发现销售单据相关模块、单据明细子表模型、或“报价单/销售订单/样品单/退货单共享一套删后重建明细逻辑”的实现。
- 未发现典型的“按 bill_id 先删除全部明细，再批量插入新明细”的代码或 SQL。

### 2. 当前项目确实存在“前端持有整份数据 + 自动保存”的相似模式

- `store/useAppStore.ts` 在前端 Zustand store 中持有整份 `processes`、`departments`、`businesses`、`tasks`、`strategy` 等数据。
- `hooks/useAppActions.ts` 中存在延时自动保存：
  - `debouncedSaveStrategy`：1 秒防抖保存战略。
  - `debouncedSaveProcess`：1 秒防抖保存流程。
  - `debouncedSaveDepartments`：1 秒防抖保存部门列表。
- `handleSetStrategy`、`setProcessData`、`updateProcessProps`、`handleSetDepartments` 会先更新前端内存，再触发延时保存。
- 该模式虽然不是 `useEffect` 直接发保存请求，但本质仍属于“前端先持有整份对象/数组，再延时回写”。

### 3. 当前项目存在“按前端整份数组做 diff 后逐条删改增”的模式

- `debouncedSaveDepartments` 与 `handleSave` 对部门数据的保存逻辑为：
  - 根据 `lastSavedDepartments` 与当前数组求差异；
  - 先删除前端认为已不存在的记录；
  - 再逐条新增/更新当前数组中的记录。
- `handleSetUsers`、`handleSetSystemRoles`、`handleSetBusinesses` 也采用类似模式：
  - 以前端当前完整数组与 `lastSaved*` 比较；
  - 删除缺失项；
  - 新增新项；
  - 更新变化项。
- 这不是“整表先删后重建”，但属于“以前端快照为基准的批处理同步”，并发风险与销售单据“先删后重建”有相似性。

### 4. 当前项目也存在“整字段覆盖”的模式

- `data.ts` 中的 `updateStrategy` 会直接 upsert 战略字段，其中 `company_okrs` 为整字段覆盖。
- `updateProcess` 会直接更新 `nodes`、`links`、`history` 等 JSON 结构字段。
- 这类保存不是明细表重建，但属于整对象覆盖，仍存在最后写入者覆盖前一写入者的问题。

### 5. 当前项目的任务模块不是“整批重建”，但前端仍持有全量数组

- `TaskCenterView.tsx`、`ExecutionView.tsx`、`WeeklyView.tsx`、`WorkbenchView.tsx`、`ReviewView.tsx` 中会在前端构造新的 `tasks` 数组并写回 store。
- 同时，多数任务落库操作调用 `addTask` / `updateTask` / `deleteTask`，数据库层是单条原子操作，而不是删除全部再重建。
- `handleSetTasks` 仍保留“整份 tasks 写回 store + 调 `saveWorkspace`”的旧入口，但 `saveWorkspace` 已不再全量保存 tasks，说明此入口更像历史遗留包装层。

### 6. 项目已尝试做“实时同步防覆盖”，但并未真正解决并发一致性

- `useRealtimeSync.ts` 监听 `tasks`、`processes`、`departments`、`strategy`、`businesses` 的 Supabase realtime 事件。
- 代码使用 `lastSaved*`、本地当前值、`updatedAt` 做以下防护：
  - 跳过回显更新；
  - 本地存在未保存改动时，跳过远端 UPDATE/DELETE；
  - 对部分对象使用时间戳判断远端是否比本地更新。
- 这些措施只能降低“自己保存后又被自己回显覆盖”的概率，不能形成真正的并发控制。

### 7. `sql/00_one_click_schema.sql` 的结构性问题会放大覆盖风险

- 当前 schema 几乎所有表都缺少统一的并发控制列与约束：
  - 没有统一的 `version` / `row_version`；
  - 只有 `processes`、`businesses` 有 `updated_at`，`tasks` 虽有 `version` 列但当前代码未使用；
  - `strategy`、`departments`、`users`、`system_roles`、`settings` 没有版本控制字段。
- 当前 schema 缺少关键外键：
  - `users.department_id` 没有外键到 `departments.id`；
  - `tasks.owner_id`、`tasks.department_id` 没有外键；
  - `processes.owner` / `co_owner` 只是文本名，不可校验引用完整性。
- 多个表把高频变化的子结构直接塞进 JSONB：
  - `departments.roles`、`role_members`、`sub_departments`、`okrs`、`reviews`
  - `strategy.company_okrs`
  - `processes.nodes`、`links`、`history`
  - `tasks.target_weeks`、`participant_ids`、`approver_ids`、`logs`
- 这些设计并不是一定错误，但在“多人同时编辑”前提下，会天然偏向整块覆盖，而不是精确合并。

### 8. 逐表判断：是否需要重构

#### `users`

- 现状：
  - 核心字段基本平坦，但 `pad_permissions`、`system_role_ids`、`custom_permissions`、`reviews` 仍是 JSONB。
  - 没有 `updated_at` / `version`，没有外键约束 `department_id`。
- 并发风险：
  - 两个管理员同时编辑同一用户权限、角色、部门归属时，容易最后写入覆盖。
  - JSONB 中的权限与角色数组不利于细粒度更新。
- 结论：
  - 需要中度重构，但不是第一优先级。
  - 最低要求是新增版本列并落地乐观锁。
  - 若做彻底治理，建议把 `system_role_ids` 改为关联表，把 `reviews` 独立出去。

#### `departments`

- 现状：
  - `departments` 同时承载部门主数据、树结构、岗位定义、岗位成员、OKR、复盘，且大量字段为 JSONB。
  - 前端类型 `Department` 也直接内嵌 `subDepartments`，说明当前是“整棵部门树”在前后端整块传递。
- 并发风险：
  - 两人分别修改同一部门的树结构、岗位成员、OKR、复盘，极易互相覆盖。
  - 删除/移动子部门时，如果另一人同时改该节点下的 OKR 或角色，会出现脏数据回写。
  - 用部门整棵树作为保存单位，会让局部修改升级为全树竞争。
- 结论：
  - `departments` 是当前 schema 最需要重构的表。
  - 需要新增表，不能只靠补一个 `updated_at` 彻底解决。
  - 最少应拆出树关系；理想情况下应把岗位、成员、OKR、复盘也拆开。

#### `processes`

- 现状：
  - 一条流程记录内含 `nodes`、`links`、`history` 三块 JSONB，前端流程编辑器按整对象更新。
  - 虽然有 `updated_at`，但更新 SQL 没有带版本条件。
- 并发风险：
  - 两人同时编辑同一流程图不同节点时，仍会整张图互相覆盖。
  - 发布版本和编辑流程若并行发生，`history` 与当前 `nodes/links` 可能被不同写入互相覆盖。
- 结论：
  - 需要重构，但可以分阶段。
  - 最低方案：保留 JSONB，补条件更新与编辑锁。
  - 彻底方案：拆 `process_nodes` / `process_links` / `process_history`。

#### `strategy`

- 现状：
  - 单行 `id='default'` 承载使命、愿景、客户/员工议题、公司 OKR。
  - `company_okrs` 为 JSONB。
- 并发风险：
  - 这是典型单热点记录，任何人修改任何一部分都会竞争同一行。
  - 一人改愿景、一人改公司 OKR，若接口仍是 upsert 单行，极易相互覆盖。
- 结论：
  - 需要重构。
  - 最低方案：按字段分版本或基于版本号条件更新。
  - 更合理方案：将 `company_okrs` 拆为独立表。

#### `businesses`

- 现状：
  - 基本是一行一业务定义，结构较扁平，仅靠 `updated_at` 标识时间。
- 并发风险：
  - 两人同时编辑同一业务时仍会最后写入覆盖，但影响面较小。
- 结论：
  - 不必优先拆表。
  - 建议补版本控制和条件更新即可。

#### `tasks`

- 现状：
  - 主体字段已相对平坦，但 `target_weeks`、`participant_ids`、`approver_ids`、`logs` 为 JSONB。
  - 表中有 `version` 列，但代码未真正使用它做并发控制。
- 并发风险：
  - 多人同时编辑同一任务时，参与人、审批人、日志等数组字段会整块覆盖。
  - 任务日志目前是整数组回写，天然不适合并发 append。
- 结论：
  - 中度重构即可，不一定要立即全面拆表。
  - 第一阶段应先把现有 `version` 真正用起来。
  - 第二阶段可考虑拆 `task_participants`、`task_approvers`、`task_logs`、`task_weeks`。

#### `system_roles`

- 现状：
  - `permissions` 为整块 JSONB。
- 并发风险：
  - 两个管理员同时编辑同一个系统角色权限树，会整块覆盖。
- 结论：
  - 不是最高优先级。
  - 最低方案：新增版本控制。
  - 若长期需要多人维护权限模型，再考虑拆为 `role_permissions` 明细表。

#### `settings`

- 现状：
  - 单行 `id='default'` 承载 `ai_settings` JSONB。
- 并发风险：
  - 与 `strategy` 相同，属于单热点记录。
  - 但当前业务频率较低，冲突概率低于战略与部门。
- 结论：
  - 不必先拆表。
  - 仍建议补版本列与条件更新。

## Proposed Changes

### 方案 A：维持当前数据模型，补齐乐观锁与冲突检测

- 适用：希望改动最小，优先控制多人同时编辑的覆盖风险。
- 核心做法：
  - 为 `strategy`、`processes`、`departments`、`businesses`、`tasks` 建立统一版本字段，如 `updated_at + version`。
  - 更新时带上“我读取时的版本号”作为条件，若版本不匹配则拒绝更新并返回冲突。
  - 前端接到冲突后，提示“数据已被他人修改”，支持刷新、对比、手工合并。
- 预期收益：
  - 解决静默覆盖；
  - 不需要立刻重构全部页面编辑模型。
- 局限：
  - 仍然是较粗粒度对象保存；
  - 合并体验依赖前端额外设计。

### 方案 A-1：最小必要 schema 重构

- 适用：希望尽快解决“静默覆盖”，但暂不大拆表。
- 涉及文件：
  - `sql/00_one_click_schema.sql`
  - `data.ts`
  - `hooks/useAppActions.ts`
  - `useRealtimeSync.ts`
- 做法：
  - 为 `users`、`departments`、`strategy`、`businesses`、`tasks`、`system_roles`、`settings` 全部补 `updated_at BIGINT NOT NULL` 与 `version BIGINT NOT NULL DEFAULT 0`。
  - 统一把更新接口改为：
    - 读取时带出 `version`；
    - 更新时 `WHERE id = ? AND version = ?`；
    - 成功后 `version = version + 1`，并刷新 `updated_at`。
  - 对 `strategy`、`settings` 这类单例表也必须带版本条件，不能继续裸 upsert 覆盖。
  - 前端在 `useRealtimeSync.ts` 中把“跳过远端变化”升级为“标记冲突并提示刷新/合并”。
- 价值：
  - 最快把“最后写入者静默覆盖”变成“可感知冲突”。
  - 为后续表结构重构打基础。

### 方案 B：把数组级批处理同步改成“记录级命令式保存”

- 适用：希望降低 `lastSaved数组 vs 当前数组` 差异同步带来的误删风险。
- 核心做法：
  - 废弃部门/用户/角色/业务定义中的“整数组 diff 后删改增”入口；
  - 改为显式的 `create/update/delete` 单记录命令；
  - 列表页面只提交用户实际操作的那一条或那几条记录。
- 预期收益：
  - 降低多人编辑不同记录时互相覆盖或误删的概率；
  - 降低失败时的中间态范围。
- 局限：
  - 需要重构现有若干列表页的保存编排；
  - 页面会从“全页一次提交”转向“操作即保存”或“记录级保存”。

### 方案 B-1：部门域优先重构为关系模型

- 适用：如果目标是“确保多人同时增删改查正常”，部门域必须优先处理。
- 涉及文件：
  - `sql/00_one_click_schema.sql`
  - `types.ts`
  - `data.ts`
  - `components/OrgView.tsx`
  - `components/StrategyView.tsx`
  - `components/ReviewView.tsx`
  - 依赖部门树/OKR/复盘的其他页面
- 推荐新表：
  - `departments`
    - 仅保留部门主数据：`id`、`name`、`manager_user_id`、`responsibilities`、`attributes`、`parent_id`、`sort_order`、`updated_at`、`version`
  - `department_roles`
    - 存部门内岗位定义：`id`、`department_id`、`role_name`、`updated_at`、`version`
  - `department_role_members`
    - 存岗位成员：`department_role_id`、`user_id`
  - `department_okrs`
    - 存部门目标：`id`、`department_id`、`year`、`period`、`objective`、`sort_order`、`updated_at`、`version`
  - `department_krs`
    - 存 KR：`id`、`department_okr_id`、`content`、`sort_order`、`updated_at`、`version`
  - `department_reviews`
    - 存复盘主记录：`id`、`department_id`、`period_key`、`reviewer_id`、`date`、`content`、`score`、`updated_at`、`version`
  - 可选 `department_review_okr_details`
    - 如果复盘详情长期复杂增长，再把 `okrDetails` 从 JSON 中拆出去。
- 为什么需要这些表：
  - `sub_departments` 改 `parent_id` 后，部门树的增删改移动可以做到单节点级操作，不再整棵树覆盖。
  - `roles` 与 `role_members` 拆表后，岗位定义和成员维护不再互相覆盖。
  - `okrs` 与 `reviews` 拆表后，战略、复盘、周任务引用都能在记录级并发控制下运行。
- 结论：
  - 对部门域，答案是“需要新增表”，而且建议新增不止一张。

### 方案 C：对复杂 JSON 字段做“子结构增量更新”而不是整对象覆盖

- 适用：流程图 `nodes/links`、战略 `companyOKRs` 这类大 JSON 结构。
- 核心做法：
  - 把当前整字段 upsert 改为子结构级 patch；
  - 或者为流程节点、连线、OKR/KR 拆分独立表，按子项保存。
- 预期收益：
  - 多人编辑同一流程或同一 OKR 的不同部分时，减少整对象覆盖。
- 局限：
  - 数据模型改动最大；
  - 需要设计 patch 协议或拆表迁移。

### 方案 C-1：流程与战略表的专项重构

- 涉及文件：
  - `sql/00_one_click_schema.sql`
  - `types.ts`
  - `data.ts`
  - `components/ProcessView.tsx`
  - `components/StrategyView.tsx`
  - `hooks/useAppActions.ts`
- `strategy` 推荐重构：
  - 保留 `strategy_profile` 单行表存 `mission/vision/customer_issues/employee_issues`。
  - 新增 `company_okrs`、`company_krs` 表存公司 OKR/KR。
  - 这样修改愿景与修改某个 KR 不再竞争同一 JSON。
- `processes` 推荐重构：
  - 若要求多人同时编辑同一流程图，新增：
    - `processes` 主表存元信息；
    - `process_nodes` 存节点；
    - `process_links` 存连线；
    - `process_history` / `process_history_nodes` / `process_history_links` 存快照。
  - 若暂不追求多人同时编辑同一张流程图，可退而求其次：
    - 保留 JSON；
    - 增加 `edit_session_lock` 或短租约锁；
    - 同时引入版本检查。

### 方案 D：保留 realtime，但改为“冲突提示优先”而不是“本地直接吞掉远端变更”

- 适用：需要在多人协作下更可预期地暴露冲突。
- 核心做法：
  - 本地有未保存改动时，不是简单 `return prevState` 跳过远端事件；
  - 而是记录冲突状态、弹出提示、允许用户查看远端版本；
  - 对关键对象提供“覆盖远端 / 接受远端 / 手动合并”。
- 预期收益：
  - 避免当前“冲突发生了但用户不知道”的隐性状态。
- 局限：
  - 仍依赖前端交互与版本字段配合才可靠。

### 方案 E-1：统一补齐关系约束与索引

- 适用：避免“数据没被覆盖但已失真”。
- 涉及文件：
  - `sql/00_one_click_schema.sql`
- 做法：
  - 增加外键：
    - `users.department_id -> departments.id`
    - `tasks.owner_id -> users.id`
    - `tasks.department_id -> departments.id`
    - 部门重构后新增表的外键链路全部补齐。
  - 增加必要检查约束：
    - `tasks.status`、`priority`、`visibility`
    - `processes.level`
  - 为高频查询与并发更新增加复合索引：
    - `tasks(owner_id, status)`
    - `department_okrs(department_id, year, period)`
    - `department_reviews(department_id, period_key)`
- 价值：
  - 即使发生并发失败，也能减少悬挂引用、脏关联、无效枚举值。

### 方案 E：后端事务化封装批处理，替代前端 orchestrate

- 适用：若后续出现类似销售单据明细、部门树、复杂列表批量编辑等场景。
- 核心做法：
  - 前端不再循环调用多个 `delete/add/update`；
  - 由后端 RPC / 事务接口一次性处理；
  - 在事务中完成版本校验、删除、新增、更新，失败则整体回滚。
- 预期收益：
  - 避免前端多次请求导致的中间态；
  - 为未来“单据头+明细”模型提供统一落地方式。
- 局限：
  - 当前仓库需要补充后端事务接口；
  - 不是最小改动方案。

### 推荐落地顺序

- 第一阶段，必须做：
  - 全表补 `updated_at + version`
  - 所有更新接口改条件更新
  - 前端冲突提示化
  - 停止对部门/用户/角色/业务定义使用“整数组 diff 同步”
- 第二阶段，优先做：

  - `strategy.company_okrs` 拆表

- 第三阶段，按协作强度决定：
  - 流程图拆表或引入编辑锁
  - 任务参与人/审批人/日志拆表
  - 权限模型细化拆表

## Assumptions & Decisions

- 决定 1：以当前仓库真实代码为分析依据，不把不存在的销售单据模块强行映射为现有实现。
- 决定 2：本次重点判断“是否存在销售单据类并发覆盖风险的同构问题”，而不是判断“是否已存在销售单据模块本身”。
- 决定 3：把当前风险分成两类讨论：
  - 前端整份状态延时回写造成的最后写入覆盖；
  - 前端整数组 diff 同步造成的误删、脏数据回写和部分失败中间态。
- 决定 4：以“解决数据覆盖问题、确保多人同时增删改查正常”为第一目标，优先级高于兼容当前 JSON 存储便利性。
- 假设：Supabase 当前未使用数据库级乐观锁、行版本检查或事务型批处理接口。
- 假设：部门域允许进行表结构重构，而不是必须永远维持 `Department` 的嵌套 JSON 形态。
