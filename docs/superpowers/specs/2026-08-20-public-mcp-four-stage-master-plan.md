# 公网 MCP 四阶段总体建设方案

## 1. 方案目标

让用户在 TRAE 中通过现有公网网站接入本系统，使用各自的系统身份查询和操作 OKR、PAD、部门、任务及流程数据。

本方案遵循以下边界：

- 系统已经部署在公网服务器；
- 继续使用现有网站域名；
- MCP 地址是现有域名下新增的接口路径，例如 `https://现有域名/mcp`；
- 不建设第二个网站，不申请新域名，不增加新公网 IP；
- 用户不安装、不运行本地 MCP Bridge；
- 第一阶段使用现有系统账号密码；
- 当前系统按“单企业、多用户”建设；
- 每个用户使用自己的账号，禁止多人共用同一个 MCP 账号；
- 完成一个阶段并经用户验收后，才允许开始下一个阶段。

TRAE 官方支持远程 Streamable HTTP MCP，也支持通过 `url` 和 `headers` 配置远程 MCP 地址及鉴权信息：

- [TRAE 添加 MCP Server](https://docs.trae.cn/ide_add-mcp-servers)
- [TRAE MCP 概览](https://docs.trae.cn/ide_model-context-protocol)

## 2. 总体架构

```text
用户在 TRAE 中提出要求
          ↓
https://现有域名/mcp
          ↓
现有服务器的 Nginx
          ↓
服务器内部 MCP 接入服务
          ↓
账号认证、会话管理、工具权限校验
          ↓
Supabase 用户 JWT
          ↓
Supabase RLS / RPC
          ↓
现有组织、用户、任务、流程、OKR 数据
```

网站原有地址保持不变：

```text
https://现有域名/
```

现有 API 保持不变：

```text
https://现有域名/api/...
```

只增加一个 MCP 接口路径：

```text
https://现有域名/mcp
```

该路径不是第二个网站，继续复用现有域名、服务器、公网 IP 和 HTTPS 证书。

## 3. 技术方案选择

### 3.1 方案 A：同服务器独立 MCP 接入进程（推荐）

```text
现有网站进程
现有 Flask API 进程
MCP 接入进程
```

三个进程部署在同一台服务器，由同一个域名统一对外。

优点：

- 不影响现有网站；
- MCP 故障不会直接拖垮现有 Flask API；
- 容易单独升级、测试和回滚；
- 后续增加 Redis、OAuth 和定时诊断时边界清晰。

代价是服务器多运行一个轻量后台进程，但用户不需要运行任何程序。

### 3.2 方案 B：把 MCP 直接集成到现有 Flask

可以减少一个服务器进程，但 MCP 长连接、会话和普通 REST API 会耦合在一起，后续维护成本更高。

### 3.3 方案 C：每个用户运行本地 Bridge

该方案不符合本项目目标，不采用。

因此，总方案采用方案 A，但公网仍然只暴露现有域名下的 `/mcp`。

# 第一阶段：公网只读 MCP 接入

## 4.1 阶段目标

让用户在 TRAE 中使用现有系统账号密码连接 `/mcp`，安全查询自己有权限查看的数据，不允许通过 MCP 修改数据。

## 4.2 实施步骤

### 步骤 1：确认部署和账号基础

检查：

- 现有域名已经启用 HTTPS；
- 确认当前 Nginx 或其他反向代理配置；
- Supabase Auth 使用 `username@app.local` 账号映射；
- `users.auth_id` 与 Supabase Auth 用户正确对应；
- 准备 Admin、Manager、Employee 三类测试账号。

### 步骤 2：增加 MCP 接入服务

在现有服务器中增加内部服务，例如：

```text
127.0.0.1:8787
```

该端口只允许服务器内部访问，不直接开放公网端口。

实现 MCP 基础协议能力：

- `initialize`；
- `tools/list`；
- `tools/call`；
- MCP Session；
- Streamable HTTP；
- 标准错误响应。

### 步骤 3：配置现有域名的 `/mcp`

Nginx 增加路径转发：

```text
https://现有域名/mcp
        ↓
http://127.0.0.1:8787
```

继续复用现有 HTTPS 证书。

### 步骤 4：实现账号密码认证

TRAE 请求携带：

```http
Authorization: Basic <账号和密码编码结果>
```

服务端认证流程：

```text
系统账号 zhangsan
        ↓
zhangsan@app.local
        ↓
Supabase Auth 登录
        ↓
取得用户 JWT
        ↓
读取 users.auth_id 对应的业务用户
        ↓
建立 MCP Session
```

Basic Auth 中的 Base64 不是加密，因此必须使用 HTTPS。

真实密码不得写进共享的项目级 `.trae/mcp.json` 或提交到 Git。每个用户应在自己的 TRAE MCP 配置中单独填写鉴权 Header。TRAE 当前官方变量引用只明确支持 `${workspaceFolder}`，因此不能假定其支持密码环境变量。

### 步骤 5：实现只读工具

第一阶段提供：

- `get_organization_info`：读取组织、战略和业务定义；
- `get_department_weekly_pad`：读取部门指定周次任务；
- `search_pad_tasks`：搜索当前用户可见任务；
- `get_personal_workbench`：读取当前用户自己的工作台；
- `get_process_sipoc`：读取流程和 SIPOC 信息。

### 步骤 6：接入现有权限

所有业务查询使用登录用户 JWT：

```text
MCP → 用户 JWT → Supabase RLS
```

禁止使用 Service Role Key 查询业务数据。

用户在工具参数中传入的 `role`、`user_id`、`department_id` 不能作为身份依据，真实身份必须来自登录会话。

### 步骤 7：增加基础安全控制

包括：

- 登录失败限流；
- 单次返回数量限制；
- 查询超时；
- 日志脱敏；
- Session 过期；
- Supabase Token 自动刷新；
- MCP 服务重启后允许用户重新连接。

## 4.3 第一阶段独立测试

### 协议测试

- TRAE 能完成 `initialize`；
- `tools/list` 返回5个工具；
- `tools/call` 返回标准结构；
- 无效 Session 被拒绝；
- 未知工具返回稳定错误。

### 认证测试

- 正确账号密码连接成功；
- 错误密码返回认证失败；
- 不存在的账号连接失败；
- 密码修改后旧密码立即失效；
- Token 过期后能够刷新；
- 刷新失败时要求重新登录。

### 权限测试

- Admin 能查看组织范围数据；
- Manager 只能查看授权范围；
- Employee 只能查看本人及被授权任务；
- Employee 查询其他部门敏感数据时不能越权。

### 安全测试

- 响应中没有密码、JWT 和 Refresh Token；
- 日志中没有完整 Authorization Header；
- HTTP 访问被强制跳转或拒绝，只允许 HTTPS；
- 连续错误登录触发限流；
- MCP 不能执行写操作。

### 业务正确性测试

将 MCP 返回结果与网站页面和数据库结果对比：

- 个人工作台任务数量一致；
- 部门周任务筛选一致；
- 任务状态、负责人、周次一致；
- 流程节点内容一致。

## 4.4 第一阶段验收标准

- 用户能在 TRAE 中连接现有域名 `/mcp`；
- 三类测试账号均能正常认证；
- 五个只读工具可以使用；
- 权限结果符合现有系统；
- 不存在越权和密码泄露；
- 现有网站、Flask API 不受影响；
- 提供部署说明、使用说明、测试报告和回滚说明。

## 4.5 第一阶段验收闸门

第一阶段完成后停止开发，由用户进行验收。

只有用户明确回复以下内容，才能开始第二阶段：

```text
第一阶段验收通过，同意开始第二阶段
```

# 第二阶段：安全写入和基础团队协作

## 5.1 阶段目标

允许用户在 TRAE 中创建、更新和提交业务数据，同时保证权限、确认、并发和审计安全。

本阶段的“团队模式”不是多人共用一个账号，而是：

```text
所有成员连接同一个 /mcp
每个人使用自己的系统账号
系统识别每个人的角色和部门
多人在同一套业务数据中协作
```

## 5.2 实施步骤

### 步骤 1：确定写入工具白名单

建议第一批写入工具：

- `prepare_create_pad_task`；
- `commit_create_pad_task`；
- `prepare_update_pad_task`；
- `commit_update_pad_task`；
- `submit_pad_task`；
- `save_review_record`。

第二阶段暂不开放：

- 批量删除；
- 删除部门；
- 删除流程；
- 修改用户权限；
- 修改系统配置。

### 步骤 2：修复和收紧写权限

在开放写工具前审计所有 Supabase RLS。

当前数据库方案中，流程表部分策略对 authenticated 用户过于宽松，第二阶段必须收紧：

- Employee 只能修改本人负责或参与的任务；
- Manager 只能管理授权部门；
- Admin 才能进行组织级操作；
- MCP 不能绕过网站原有权限。

### 步骤 3：实现两步确认

写操作不能一次直接执行：

```text
用户提出修改
    ↓
prepare 工具生成修改预览
    ↓
TRAE 向用户展示旧值和新值
    ↓
用户明确确认
    ↓
commit 工具执行
```

确认令牌需要绑定：

- 当前用户；
- 工具名称；
- 完整参数摘要；
- 过期时间；
- 一次性状态。

参数发生变化后必须重新确认。

### 步骤 4：实现事务和乐观锁

继续使用现有 `row_version`：

```text
读取 row_version=5
        ↓
提交更新时仍要求 row_version=5
        ↓
数据已被其他用户改成 row_version=6
        ↓
拒绝覆盖并提示重新读取
```

复杂写操作使用数据库 RPC 或事务，避免只写入一部分数据。

### 步骤 5：增加幂等控制

TRAE 可能因为超时而重试同一请求。

每次写入携带唯一请求编号：

- 重复请求不能创建两条任务；
- 已完成请求直接返回第一次结果；
- 失败请求可以安全重试。

### 步骤 6：增加审计日志

记录：

- 谁操作；
- 何时操作；
- 使用哪个 MCP 工具；
- 修改哪个业务对象；
- 修改前后摘要；
- 成功或失败；
- 请求编号。

不得记录密码、Basic Header 或 JWT。

### 步骤 7：实现基础团队协作

包括：

- 指定负责人；
- 添加参与人；
- 添加审批人；
- 提交任务；
- 查询团队任务；
- 管理者查看部门执行情况。

所有成员仍然使用自己的账号，禁止共享团队密码。

## 5.3 第二阶段独立测试

### 写入权限测试

- Employee 创建自己的任务成功；
- Employee 修改他人无关任务失败；
- Manager 管理授权部门成功；
- Manager 修改非授权部门失败；
- Admin 按配置拥有组织级权限。

### 确认机制测试

- 未执行 `prepare` 不能直接提交；
- 过期确认令牌不能提交；
- A用户的确认令牌不能被B用户使用；
- 修改参数后原确认令牌失效；
- 同一个令牌不能执行两次。

### 并发测试

- 两人同时修改同一任务；
- 后提交者收到版本冲突；
- 不会静默覆盖前一个人的内容。

### 幂等和事务测试

- 同一创建请求重试3次，只生成1条任务；
- 数据库中途失败时不留下半成品；
- 超时重试能够取得第一次执行结果。

### 审计测试

- 每次成功写入都有审计记录；
- 失败写入也记录错误码；
- 审计记录不能被普通员工修改；
- 日志不包含密码和 Token。

## 5.4 第二阶段验收标准

- 至少三类角色完成真实写入测试；
- 两步确认有效；
- 越权写入全部被拒绝；
- 并发修改不会覆盖数据；
- 重复请求不会产生重复数据；
- 所有写入可以追溯；
- 第一阶段全部测试继续通过。

## 5.5 第二阶段验收闸门

第二阶段完成后停止开发。

只有用户明确回复以下内容，才能开始第三阶段：

```text
第二阶段验收通过，同意开始第三阶段
```

# 第三阶段：真正的 KR 进度管理和趋势诊断

## 6.1 阶段目标

把目前的 KR 字符串数组升级为结构化、可记录历史、可计算趋势、可诊断风险的 KR 管理体系。

## 6.2 实施步骤

### 步骤 1：建立结构化 KR 模型

#### Objective

- 目标名称；
- 所属周期；
- 所属部门或个人；
- 负责人；
- 权重；
- 状态。

#### Key Result

- KR 名称；
- 指标类型；
- 起始值；
- 目标值；
- 当前值；
- 单位；
- 增长、下降或区间方向；
- 开始日期；
- 截止日期；
- 负责人；
- 权重；
- 置信度；
- 版本号。

#### KR进度记录

每次更新保存独立快照：

- 本次值；
- 进度百分比；
- 更新说明；
- 风险状态；
- 更新时间；
- 更新人；
- 数据来源。

历史记录只能追加，不能覆盖。

### 步骤 2：迁移现有 KR

现有 KR 字符串无法可靠判断起始值、当前值、指标方向和统计口径，因此不能完全自动迁移。

迁移流程：

```text
读取旧 KR 字符串
      ↓
生成迁移建议
      ↓
用户人工确认指标和目标
      ↓
写入新结构
      ↓
保留旧内容用于核对
```

### 步骤 3：实现进度计算

增长型：

```text
进度 = (当前值 - 起始值) ÷ (目标值 - 起始值)
```

下降型：

```text
进度 = (起始值 - 当前值) ÷ (起始值 - 目标值)
```

区间型指标需要设置合理范围，不能直接使用增长公式。

### 步骤 4：实现时间期望进度

系统计算并对比：

- 实际进度；
- 目标时间进度；
- 进度差；
- 最近更新速度；
- 预计期末值；
- 数据多久没有更新。

第一版使用确定性规则，不让 AI 自己猜数字。

### 步骤 5：实现趋势诊断

输出状态：

- `on_track`：正常；
- `at_risk`：存在风险；
- `behind`：明显落后；
- `insufficient_data`：数据不足。

AI 只负责把计算结果解释成人能理解的文字，不能自行修改数值和风险等级。

### 步骤 6：实现 KR 工具

建议增加：

- `get_kr_dashboard`；
- `get_kr_history`；
- `prepare_update_kr_progress`；
- `commit_update_kr_progress`；
- `diagnose_kr_trend`；
- `get_at_risk_krs`。

### 步骤 7：改造系统页面

网站同步增加：

- KR 指标配置；
- 进度录入；
- 历史趋势图；
- 风险状态；
- 数据更新时间；
- 诊断依据；
- 迁移确认界面。

避免网站使用旧数据、MCP 使用新数据的两套逻辑。

## 6.3 第三阶段独立测试

### 计算测试

- 起始0、目标100、当前40，进度必须为40%；
- 起始100、目标60、当前80，下降型进度必须为50%；
- 起始值等于目标值时拒绝保存；
- 超过目标时按照配置允许超过100%或封顶；
- 缺少当前值时返回数据不足。

### 趋势测试

- 时间过去50%、实际进度40%，差值为负10个百分点；
- 连续多周无进展时识别风险；
- 最近速度不足时预测无法达标；
- 没有历史记录时返回 `insufficient_data`；
- AI 诊断中的数字必须能在计算结果中找到依据。

### 历史测试

- 每次更新生成新快照；
- 修改当前进度不覆盖历史；
- 历史顺序正确；
- 不允许普通用户修改他人的历史记录。

### 迁移测试

- 旧 KR 保留；
- 自动识别不确定时必须要求人工确认；
- 迁移失败可以回滚；
- 迁移前后数量可以核对；
- 未迁移 KR 仍然可以只读查看。

### 权限测试

- Employee 只能更新本人负责的 KR；
- Manager 查看授权部门；
- 非授权部门数据不能访问；
- 所有 KR 更新写入审计日志。

## 6.4 第三阶段验收标准

- 至少选取10个真实 KR 完成迁移；
- 用户人工核对计算结果；
- 历史趋势可以在网站和 TRAE 中一致显示；
- 风险诊断有明确的数据依据；
- 数据不足时不生成虚假结论；
- 第一、第二阶段回归测试全部通过。

## 6.5 第三阶段验收闸门

第三阶段完成后停止开发。

只有用户明确回复以下内容，才能开始第四阶段：

```text

```

# 第四阶段：企业级认证、团队管理、预警和高可用

## 7.1 阶段目标

把已经验证的 MCP 能力升级为可长期运营的企业级能力。

默认仍按“单企业、多成员”建设。如果未来需要为多家公司提供 SaaS 服务，需要单独增加多租户改造，不能简单依靠部门权限代替租户隔离。

## 7.2 实施步骤

### 步骤 1：升级认证方式

Basic Auth 只作为早期方案，因为 TRAE 配置中的 Basic Header 实质上等价于保存系统密码。

第四阶段升级为：

- 可撤销的个人 MCP Token；或
- OAuth 2.1 授权；
- 单独控制 MCP 登录权限；
- 用户离职后立即撤销；
- 不再把系统登录密码长期保存在 TRAE。

Basic Auth 与新认证短期并行，用户迁移完成后再关闭。

### 步骤 2：Redis 会话和多实例

将内存 Session 迁移到 Redis：

- 多个 MCP 实例共享登录状态；
- 单个实例重启不要求全部重新登录；
- 支持负载均衡；
- 支持统一撤销会话。

### 步骤 3：团队管理后台

增加 MCP 管理功能：

- 是否允许某用户接入；
- 允许调用哪些工具；
- 只读或可写；
- 每日调用额度；
- 强制撤销会话；
- 查看审计记录；
- 按角色配置工具权限。

团队成员仍使用独立身份，不共享账号。

### 步骤 4：定时任务和主动预警

MCP 主要响应客户端请求，不能把“用户没有打开 TRAE 时主动通知”完全寄托在 MCP 上。

正确结构：

```text
独立调度器
   ↓
定时计算逾期任务和 KR 风险
   ↓
生成 alerts 记录
   ↓
网站通知 / 邮件 / 企业微信 / 钉钉
```

MCP 增加：

- `get_my_alerts`；
- `get_department_risks`；
- `mark_alert_read`。

这样即使用户没有连接 TRAE，预警也不会丢失。

### 步骤 5：监控和告警

监控：

- MCP 请求量；
- 成功率；
- 响应时间；
- 认证失败次数；
- Supabase 错误率；
- 工具调用分布；
- 定时任务是否按时运行；
- Redis 和数据库状态。

日志只记录必要标识，继续禁止记录密码和 Token。

### 步骤 6：备份与恢复

建立：

- 数据库定期备份；
- Redis 故障恢复方案；
- 配置备份；
- MCP 版本回滚；
- 审计日志归档；
- 定期恢复演练。

### 步骤 7：容量和安全加固

包括：

- 账号和 IP 限流；
- 请求体大小限制；
- 工具超时；
- 输入注入测试；
- 敏感字段过滤；
- 依赖漏洞扫描；
- 并发和压力测试。

## 7.3 第四阶段独立测试

### 认证测试

- Token 或 OAuth 登录成功；
- Token 撤销后立即或在约定时间内失效；
- A用户 Token 不能访问B用户数据；
- 已禁用用户不能连接；
- Basic Auth 关闭后旧配置失效。

### 高可用测试

- 两个 MCP 实例共享 Session；
- 关闭一个实例后用户连接不丢失；
- Redis 短暂异常时返回明确错误；
- Redis 恢复后服务正常；
- 重复请求不会因多实例重复执行。

### 调度器测试

- 同一预警不会重复生成；
- 风险消失后状态正确更新；
- 定时任务失败会触发监控告警；
- 补跑任务不会产生重复通知；
- 用户未打开 TRAE 也能通过配置渠道收到通知。

### 团队管理测试

- 管理员可以停用某用户 MCP 权限；
- 工具白名单即时生效；
- 只读用户不能调用写工具；
- 普通用户不能查看全公司审计日志；
- 所有管理操作可追踪。

### 压力和恢复测试

初始建议基线：

- 50个并发 MCP 用户；
- 普通查询 P95 小于3秒；
- 服务错误率低于1%；
- 单实例停止后服务仍可用；
- 备份可以实际恢复到测试环境。

具体容量指标可在第四阶段开始前根据实际用户数调整。

## 7.4 第四阶段验收标准

- 用户不再需要把系统密码长期保存在 TRAE；
- 多实例和 Redis 正常工作；
- 用户和工具权限可以集中管理；
- 定时风险诊断不会重复执行；
- 主动通知有独立可靠渠道；
- 审计、监控、备份、恢复均有实际测试证据；
- 前三个阶段全部回归测试通过。
